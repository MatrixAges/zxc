# 生成分析工作区释放对照

## Intent：最终目标

区分整表快照复制本身与 arena 嵌套保留的成本。仅改变两个已由分配栈定位的短期 arena 的 backing，使 deinit 实际归还其内存；不改变分析、快照或固定点算法。

## Data：可用证据

此前 expression_analysis 单入口累计复制 36.09 GiB，最大扩容来自 iteration_buffer/analysis 与 buffer_call/analysis/versions。基线生产来自 d547ddb36，当前整合提交 8fc8c3db8 没有改变生产源码。

两个临时变更分别位于 analyzeWithCalls 与 versions.check。前者仅向调用方复制 ExprId 和无切片的 Call 记录；后者只返回 bool。局部 arena 之外无这两处工作区结果借用的设计契约。

## Edges：边界与限制

本轮只在临时副本把这两个 arena 的 backing 改为 page_allocator，生产代码不改。这是隔离生命周期影响的诊断，不是最终 allocator API 设计；正式实现需要显式传入可释放的工作区 allocator，并保留调用方分配控制和错误语义。不能将这两行修改直接当成可发布方案。

同一驱动、工具链、输入与 safe 优化级别，分别编译基线及变体生成器；生成器构建成本不计入运行。独立执行两者，以 time -l 记录编译墙钟和 RSS，并与已有输出逐字节比较。机器仍可能有并行干扰，不将小幅时间差作为收益。

## Answer：交付与成功标准

交付原始命令、两轮资源数据、产物比较、临时源码归档及结论。若仅释放边界就降低峰值，说明需要先明确工作区生命周期；即使结果一致，也不替代非法输入、分配失败等行为验收。本轮不新增或运行功能测试。

## 对照结果

两个生成器均成功构建，随后分别执行同一入口；两次运行均退出 0。每次生成的两个 Zig 文件与最初基线逐字节一致。

| 指标                |                 原始嵌套 arena | 两个工作区直接使用 page_allocator |
| ------------------- | -----------------------------: | --------------------------------: |
| 总墙钟（time -l）   |                       32.15 秒 |                          40.96 秒 |
| user / system       |                31.29 / 0.76 秒 |                   35.32 / 5.53 秒 |
| infer               |                      15.384 秒 |                         15.323 秒 |
| emit                |                      16.718 秒 |                         25.591 秒 |
| 最大 RSS            | 3,889,692,672 字节（3.62 GiB） |    1,455,951,872 字节（1.36 GiB） |
| page reclaims       |                        971,596 |                        10,705,993 |
| page faults / swaps |                          0 / 0 |                             0 / 0 |

峰值 RSS 降低 **62.6%**，但 emit 耗时增加 **53.1%**。infer 基本保持原有量级，变化集中在本次修改的生成阶段。system 时间和 page reclaims 明显增加，与反复申请、归还工作区页面的成本一致；仍保留机器并行干扰的限制，不把一次对照当作稳定吞吐统计。环境快照有其他会话的 Zig 进程，约占 7.04 GiB RSS，未终止该进程。

此结果支持两个判断：

1. 工作区生命周期确实是生成峰值的重要原因；两个局部释放边界的改变就显著降低了 RSS。
2. 直接替换为 page_allocator 不是合适的生产方案。下一步应验证显式工作区复用，在保留调用方 allocator 控制的同时减少系统分配；若要进一步降低复制成本，还需要单独优化状态保存粒度。

本轮没有减少 snapshot/object cache 的算法执行次数；因此不能将峰值下降说成整表复制问题已经解决。也不能把 1.36 GiB 视为理论最低内存，它仍包含当前分析及其他存活数据。

证据包括 `释放对照统计.json`、两组构建/运行命令与日志、`释放对照环境.json` 和 `释放对照源码.tar.gz`，均按仓库规则本地忽略。统计记录两份生成器 SHA256、退出状态及输出 SHA256。生产代码与原基线相同。

## 自我批判

产物一致只证明固定成功路径；对照也无法消除实际复制成本。若内存降低但耗时增加，应分别报告，并继续评估可复用工作区而非把反复页分配作为最终方案。

## 可复用工作区实验边界

在上一轮释放副本上继续改变生命周期，保留全部分析算法：flow.functions/entry 各自持有一个版本分析 arena，在每个 versions.check 前 reset 并保留容量；iteration_buffer.init 持有一个 arena，供同一次 collect 的多个字段分析顺序复用。工作区通过参数传入，不使用全局状态，在所属调用结束时 deinit。

versions.check 只返回 bool；analyzeIn 在重置前一轮工作区前，上一轮已把更新与调用记录复制到输出 allocator。其他没有传入该 workspace 的路径继续使用上一轮独立 arena；因此这只是有明确作用域的局部复用实验，不能宣称覆盖所有分析工作区。临时 backing 仍为 page_allocator，正式设计尚需保留调用方的分配控制。

比较同一入口的耗时、RSS 与完整输出。若复用保留容量显著增大峰值或没有收回分配成本，应如实记录；不以“复用”命名直接认定优化成功。

### 单入口复用结果

复用变体退出 0，两个生成文件与最初基线逐字节一致。总墙钟 32.18 秒、user 31.42 秒、system 0.66 秒；infer 15.679 秒、emit 16.451 秒，最大 RSS 1,457,307,648 字节（约 1.36 GiB）。

相比原始基线 32.15 秒、3.62 GiB，耗时保持同一量级，峰值下降约 62.5%；相比逐次释放版本 40.96 秒、1.36 GiB，局部复用消除了本轮可观察到的大部分额外分配成本。不声称 0.27 秒 emit 差异是稳定加速，机器并行干扰仍在。

下一步把同一副本用于原 55 入口、94 产物的主生成批次，比较全部产物和批次资源。独立 lexer 未涉及这些工作区，沿用已记录基线，不把它混进本批次时间。

### 主生成批次结果

同一临时复用实现完成 55 个入口，退出 0；输出 94 个文件、52,020,815 字节，**94/94 与原基线逐字节一致**。原 1,288 个输入文件的 SHA256 核对无差异。

| 主生成批次指标 |     原无探针基线 |        可复用工作区诊断 |
| -------------- | ---------------: | ----------------------: |
| 墙钟           |        152.87 秒 |               155.31 秒 |
| user / system  | 148.64 / 3.53 秒 |        151.23 / 3.71 秒 |
| 最大 RSS       |         3.62 GiB |            **1.47 GiB** |
| 产物           |          94 文件 | 94 文件，与基线完全一致 |

复用批次 RSS 为 1,576,366,080 字节，比基线降低 **59.5%**。本轮含阶段输出的诊断开销，且存在其他会话的 Zig 编译；不把 2.44 秒差异解释成稳定退化或加速。批次内部累计 infer 78.975 秒、emit 76.063 秒；仍未解决推导重复校验及整表复制的时间成本。

这是主生成批次，不含独立 lexer 的 0.84 秒历史测量，也不含生成器构建和 Zig 后端。产物完全一致意味着本轮没有减少后端输入规模；没有重新测量或声称改善后端 5.27 GiB 的峰值。

原始证据为 `复用对照统计.json`、`复用批次统计.json`、相应命令/构建/运行日志、`复用批次输入核对.json` 和 `复用批次环境.json`。`复用对照源码.tar.gz` 收录五个临时 genz 修改文件及五个驱动文件，`复用对照差异.txt` 保留精确差异。与生产 genz 全目录比较，确认仅这五个文件变化；没有将副本替换进生产目录。

结论：明确作用域内的复用能够在本负载下保留大部分内存下降，同时避免逐次页分配的明显额外成本。后续正式接口应从 emit/分析调用方传入 backing，明确哪个 owner 持有、何时 reset/deinit，保留原有分配失败传播；不能发布硬编码 page_allocator 的诊断副本，也不能宣称已通过错误路径或所有权完整验收。
