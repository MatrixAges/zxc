# 工具启动阻塞诊断与恢复

## IDEA

- Intent：定位构建与格式化长时间不返回的原因，恢复工具执行并验证原有修复。
- Data：Zig、fd 和生成测试程序处于 U 状态，累计 CPU 时间为零或接近零；TERM 和 KILL 后仍存在。磁盘可用约 910 GiB，交换空间使用约 32 MiB。未签名 Zig 和 fd 的本地签名副本立即输出原版本。
- Edges：不关闭系统安全服务，不修改 Gatekeeper/SIP，不删除构建缓存，不干预其他聊天的进程。当前无免密管理员权限，未取得内核等待栈，不能断言具体内核锁或服务是根因。
- Answer：恢复 Zig 与 fd 的可执行文件，保留原文件备份和 SHA-256，运行真实格式化与原深度重放。

## 证据与结论

1. 同一批进程持续等待超过 40 分钟；停止父任务后，若干子进程仍处于 U 状态。
2. codesign 显示原 Zig 和 fd 完全没有签名；可正常运行的 Homebrew rg 使用 ad-hoc 签名。
3. fd 临时副本仅添加本地 ad-hoc 签名，立即返回 fd 10.4.2。
4. Zig 临时副本仅添加本地 ad-hoc 签名，立即返回 0.17.0。
5. 验证签名后，将原工具重命名为 unsigned-backup-20261009 备份，再将签名副本原子替换到原路径。原路径版本命令与 zig fmt 均成功退出。

证据支持故障位于当前主机的未签名可执行文件启动路径，不能归因于本次项目编译逻辑、缓存锁或依赖图递归。签名恢复了这两个工具的执行能力；尚未修复系统底层的未签名程序启动故障。其他新生成的未签名可执行文件仍可能受影响。

## 恢复范围

精确路径、备份与前后散列见修复文件记录.json。未改动 Zig 标准库、工具版本、项目缓存及测试输入。深度重放使用 --test-no-exec 编译，给生成的可执行文件添加本地签名后执行；签名只服务于本机执行恢复，不变更源码语义。

## 自我批判

这是有对照证据的工具恢复措施，并不等于完成操作系统根因修复。旧 U 状态进程未能清除；正常重启系统可能仍是清理这些进程和恢复一般未签名执行能力所需的操作。本轮未擅自重启电脑，亦未因旧签名日志中的一般校验错误就重启安全服务。

## 验证

- Zig 原路径 version：0.17.0，退出 0。
- fd 原路径 --version：10.4.2，退出 0。
- 项目修复文件 zig fmt：退出 0。
- 原有深度重放：编译退出 0，运行退出 0。65、129、193、255 层分析和提取通过；257 层返回原深度限制诊断。沿用现有输入与默认栈限制。
