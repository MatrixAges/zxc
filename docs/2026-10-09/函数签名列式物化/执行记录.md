# 函数签名列式物化执行记录

## Intent：最终目标

让正式产物的函数签名由 RX/ZX 按规划直接物化为列，消除宿主逐行选择和编号变换，以及不必要的中间签名行数组。

## Data：可用证据

core 的 SignatureTable 保存文件、输入/输出类型、ownership 与完整原生调用元数据，共 15 列，at() 提供兼容行视图。种子 builder 使用 SignatureStorage；原生缓存构造直接借用同一 arena 的 FunctionTable 列。正式产物由 materializing/signatures.zx 和 signature_ids.zx 生成表，RX 显式连接原生表成功分支与签名阶段；prepared/declarations.zig 已删除。

FunctionTable.native_inputs 从可选 NativeType 内嵌结构改为可选名称数组，at() 恢复既有 NativeType 公共行视图。null、空数组、含 null 的数组三个含义分别保留。其序列化变化由 ir_version 36 区分，模块缓存表形状变化由 zxc.module.v3 区分。所有直接联结、普通恢复、原生恢复及 codec 解码入口均在签名 at() 前检查列结构。

## Edges：边界与限制

输入完整性来自 artifact.extract 对整个 Program 的验证，签名 ZX 算法不是未验证外部表的公开入口。函数编号严格保持计划顺序，原生产物与 function_imports 保持同序。数字与标志列直接接管；名字、错误、原生输入名等借用内层列表先复制列表再复制字符串，避免改变源分析。

宿主描述符在栈上按字段组装；数组底层内存没有复制。描述符字段顺序不必与生成结构相同，仍保持逐列编译期类型检查。缓存旧形状明确拒绝，没有双格式猜测或兼容兜底。

## Answer：交付与验证

标准 `zig build -j2` 返回 0，随后 `--verbose` 命令复核同样返回 0。采用本轮完整生成依赖的 Zig 专项共 67 项：65 通过、2 失败；真实 CLI 持久缓存 5 项全部通过。因此总计 70 项通过、2 项既有失败，不能报告为全部通过。

两项失败均为 ownership/input/modules.zig 的 map 输出 ownership 断言（含其分配失败驱动）。在前一提交 d8d1522a1 源码、同一当前 ownership 等生成依赖、前一提交的 artifact_prepare 接口下复核，仍为相同 2 项失败。签名往返的 ownership 整列相等断言通过，原生签名、缓存格式与结构、生命周期、联结冲突等其余专项通过。新增 ZX 文件为 23、55、38 行。正式源码 diff 空白检查通过，草稿同步最终实现。未新增测试、未执行全量、未使用浏览器；现有测试只适配真实列形状、版本号和等价的列断言。

## 自我批判

首次实现错误地假设宿主和 ZX 规范化字段顺序相同，直接指针借用被编译期偏移校验拒绝。修正为按字段组装栈上列描述符，没有放松 borrow 校验或复制数组；失败日志单独保留。只读复核未发现调用遗漏，但编译仍发现这个布局问题，说明静态审查不能替代真实实例化。

初次文件检索还漏掉 TypeScript 持久缓存测试中的 v2 标记；扩大到所有 packages 后已同步为 v3。现有测试不新增或弱化断言：ownership 整列比较包含长度，fallibility 仍只改原生行，NativeType{} 仍等价于单个 null 名称。

此阶段迁移了函数签名规则和正式物化，不代表全部状态模型已经由 RX/ZX 定义。core 仍保存宿主列描述及种子 storage，节点复制和产物外层调度仍待迁移。不得以构建通过替代完整自举的传递依赖验收。

## 验证依赖审计修正

首次专项参数继承了历史生成目录，在排查两个所有权用例失败时发现 ownership.zig 与本次标准构建不同。前一提交对照也沿用同一旧目录，因此该对照只能定位验证依赖不一致，不能证明当前源码有回归。旧结果已归档，不纳入最终通过数量。

从本次标准构建的实际编译命令重建全部模块图：生成器源码、ABI、词法器、标准库目录和选项均采用该构建产物，仅将根入口换成既有测试并使用 Debug。所有专项据此重跑，不只替换出现失败的 ownership 单个模块。今后不得将旧参数中的生成缓存路径视为当前编译器依赖。

使用完整新依赖后，两项所有权断言仍失败；旧缓存并非该缺陷的唯一原因。标准构建与专项路径复核另有 87 个路径变化，其中 86 个生成模块及 ABI 字节完全相同，只有 CLI 专属 cache_identity 内容不同，Zig 专项根入口不使用它；CLI 5 项验证使用实际最终可执行文件。路径与内容核对见构建与专项依赖核对.json。

## 下一优先修复：聚合字段所有权精度

已确认普通集合方法被降为普通循环。循环状态中的借用 source 与独立 result 被当前所有权机概括为单一 Borrowed，再由 scope、object 缓存等整树赋值传播，读取 result 字段时也成为 Borrowed。此缺口在本轮签名迁移之前存在，没有修改测试预期或加入 map 特例。

通用修复必须先建立 object/tuple 表达式结果的字段事实，与 memory.memo 的求值缓存资格分离；通过绑定、投影、分支和缓存按字段传递。随后为每个活动循环保存 initial/head/body，按引用叶的单调 join 求固定点，覆盖跨字段依赖、嵌套循环、零次与后置循环及外层状态。现有 places.combine 非交换，不能直接当固定点 join。不能只修改 iteration 初值而保留 scope 和 object 的整体压平。

签名表示迁移作为独立节点提交；字段事实和循环固定点是紧接着的优先修复，完整目标保持未完成。
