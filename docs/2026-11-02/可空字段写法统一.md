# 可空字段写法统一

## Intent：最终目标

把维护中的可空对象字段统一为 `a?: A`，同时更新生成源、示例和应用指导，避免
重新生成旧写法；继续沿用现有 Optional 类型语义和零成本生成。

## Data：可用证据

seed 与正式 ZX 对象类型解析器均已支持字段名后的 `?`，两种写法生成相同类型。
当前存在 `a: A[]?`、嵌套对象字段以及声明接口中的旧写法，生成器也会重新输出。

## Edges：边界与限制

- 只把字段类型最外层 Optional 移到字段名后；`a: A?[]` 的可空元素不能移动。
- 独立别名、元组元素、类型参数和函数返回的 `A?` 没有字段名，保留其类型表达式。
- 不新增 `const a?: A` 等声明语法，不改变字段缺省规则、公共类型形状或运行时表示。
- 复用真正的类型解析器确定编辑位置，保留注释；不能用全仓正则替换 `?`。
- 不新增测试，不做这类语法等价修改的性能对照；用归一化 AST、现有检查及生成
  源自检证明改写前后类型和行为一致。历史交接记录与明确旧语法诊断材料保留原意。

## Answer：交付与成功标准

交付全部可解析维护源码及生成源的统一写法、同步文档、剩余形式的分类说明和
现有检查证据。按完整语法规范职责提交并推送；编译器完整自举仍继续。

```mermaid
flowchart LR
    S[ZX / 原生声明 / 文档与生成源] --> P[现有 Parser / 类型 AST]
    P --> F[最外层可空对象字段]
    F --> E[字段名后插入问号 / 删除对应后缀]
    E --> V[重新解析 / 归一化 AST 相等]
    V --> C[源头自检与既有检查]
```

## 实施结果

- 185 个维护中的 ZX 和 `.d.zx` 文件，共 262 个字段改为字段名后的 `?`。
  迁移工具复用仓库 seed Parser，对每个最外层 Optional 字段重新解析类型，准确
  找到对应的后缀 token，保留内部可空层级和注释；工具仅在 `/tmp`，没有添加新
  编译器规则或第二套类型解析器。
- RX 内联 Args 类型、六个 Zig 文件中的既有样例及运行时 JSON 枚举样例同步。
  更改已有样例，没有新增用例或放宽任何断言。
- 12 个生成源同步，重新生成现有目录和诊断 catalog；另外两个手写 catalog 中
  的三个字段也经同一 Parser 改写并验证类型 AST。七个 catalog 的记录、期望诊断
  及结果保持原意，只调整其中的源码。
- 官网中文、英文、日文、韩文的类型与语法参考，以及应用编码约定和仓库规则
  同步。区分 `items?: T[]` 和 `items: T?[]`，独立类型表达式保留后缀形式。

## 验收证据

- 原有 185 个修改文件在迁移、重新生成、排版之后，忽略源码位置的类型及程序
  AST 摘要全部相同。嵌入源码与 catalog 迁移也各自进行改写前后 AST 对照。
- 最终重扫 2982 个维护中的 ZX 文件，所有可解析对象类型中待迁移的最外层
  Optional 后缀字段为零。纯函数声明文件的空类型头不是错误；历史快照和有意
  非法的类型解析诊断输入不按正常源码改写。
- 12 组现有生成器 `--check` 全部通过，正式生产 RX/ZX 格式检查通过。
- 编译器现有 372/372 检查、自举编译器构建及正式 CLI 构建通过。
- 新构建的 1701 个自举生成文件与迁移前逐字节相同，仅排除输入指纹文件
  `.zxc-inputs`。没有为等价语法修改重复进行性能对照或三阶段重建。
- 原始迁移、AST、生成器和构建证据在 `/tmp/zxc-nullable/`；`git diff --check`
  用于本次 diff 排版复核。

## 自我核对

本次是既有语法的全仓字段规范化，没有更改 Optional 类型模型和运行时表示，
也没有新增局部 const 或原生函数参数的 `name?: T` 语法。后者当前仍采用类型
表达式，不能在没有解析支持时机械移动标记。`Node?[]` 等可空元素不是遗漏，
把它们改成可空列表会改变含义。未把历史文档快照改写成当前实现，避免伪造历史。

现有 formatter 能保留新的字段写法；这次没有增加将所有旧语法自动转换的新
formatter 规则。生成源和规范负责维持新写法。完整编译器自举仍未完成。
