# 共享初始化列的原地压缩

## Intent：最终目标

在一次类型声明初始化结束后，将本轮类型并入共享名义身份表，继续保留原有类型编号规则、冲突诊断及前缀内容，同时消除 shared_types.resolve 对既有类型前缀和 origin 列的完整复制。此阶段为完整接口所有者迁移提供基础，不等于整条原生接口链已经零复制。

## Data：可用证据

原实现将共享 origins 整表复制到 declared，再将类型 prefix 复制到空 Pool。新实现使用现有两套明确拥有容量的 storage，不从 const slice 猜测 owner：

1. 记录原 origin 数量，直接追加本轮来源；完成追加后才取得完整源视图。
2. 将 TypeStorage 和 Origins.Storage 元数据转交 Pool，清空原 owner 的元数据；无条件 defer 负责交回。
3. retainPrefix 仅缩短使用长度，保留原容量和未消费尾段字节。
4. 复用现有 appendFrom 的类型验证、preflight、RX merge 和映射逻辑，按源行顺序向前压缩。
5. 成功后更新 resolved 编号；失败则只保留原前缀并终止本次分析。

四处生产修改分别属于 core 的类型列存储、compiler 的 origin 列存储、link Pool 与共享分析适配。没有增加新的运行库或语义解释层。

### 前向写入的依据

类型结构验证同时在 seed 和 generated 路径中要求 object/tuple/names 的 first 等于该 payload 当前结束位置，最终结束位置等于整列长度。因此合法源表没有 payload 空洞、重叠复用或倒序区间。

合并每个源行最多保留一个目标行，且保留行的 payload 数量不增加。appendType 在写入之前已经读取当前 row，并将引用重映射到独立临时区；现有 copy 为名字与成员建立需要的拥有化值。目标写游标不超过当前源行，已读位置可覆盖，未来行的 header/payload 不受影响。

origin 旧前缀可维持既有顺序；本轮新 tail 由 produce 按类型编号递增追加。preflight 提前建立 source type ID 到 origin 下标的映射。目标新增 origin 数量不超过已读源 nominal 数量；appendOrigin 在写入前已经读取并复制当前来源，随后使用目标 label。

原 storage 的容量足以容纳整个 source；目标每列不会超过原 source 长度。因此压缩期间不需要 realloc。Pool 成功后对八个类型列和五个 origin 列逐一断言 backing pointer 与保存的 source 相同。

### 首轮失败与修正

首轮误用了 Zig ArrayList.shrinkRetainingCapacity。当前 Zig 标准库的该方法会先把移除范围写为 undefined，再缩短长度。结果源尾段在验证前就被破坏，生成 lexer/parser 报 InvalidModule。

修正为 retainPrefix：TypeStorage 先计算前缀各列长度，再只赋 items.len；Origins.Storage 只重绑定 items[0..len]。二者不调用标准库 shrink、不释放内存、不写 backing bytes。这是保留源尾段所必需的行为，不是为了忽略验证错误。

## Edges：边界与限制

- compact 仅用于已初始化、拥有完整列容量的内部存储；first 与 origin_count 由初始化前的 owner 记录。它先取得 prefix 再进入完整验证，不是接受任意未校验缓存字节的公开安全入口。
- 完整源视图在截短之前保存，origin view 在 staging 完成之后保存。普通 appendFrom 不因此获得任意源/目标别名写入承诺。
- 失败不能恢复原 source 长度：尾段可能已经被覆盖。只保留未修改的前缀；resolved 仍可能包含旧尾段编号，调用者必须终止本次分析，不得捕获错误后继续使用 Types。
- owner 归还按 defer 顺序执行，避免 error 路径丢失当前容量或访问已清空的元数据。
- 当前调用者使用分析 arena，字符串的必要拥有化及丢弃尾段的临时存储在 arena 结束时回收；本阶段没有声称所有字符串分配已消除。
- native、普通源模块、external signature 入口仍会将既有 TypeTable 接入新的 Types owner。缓存恢复与 compiled loader 也仍复制当前前缀；这些是下一步统一 Project 存储与事务式追加的范围。

## Answer：交付与自我批判

修正后五项既有专项 native-declarations、nominal-origins、semantic-cache、type-resolution、module-artifacts 共 60/60 构建步、119/119 测试通过。最终主构建 36/36 步通过。未新增测试、未运行全量测试。

自审重点是物理布局与失败语义，而不仅是删除 appendTable/appendDelta 的代码行。首轮 shrink 的 poisoning 证明“保留容量”并不等于“保留字节”；已按标准库实现修正并重新验证。还明确区分了保留 prefix 与恢复原完整状态，未将失败尾段重新发布。

后续 Project owner 迁移必须同时覆盖无缓存 native、source、external、compiled 和缓存恢复。缓存恢复可能在类型合并之后发现依赖不匹配并返回 null，因此需要事务式保留原列长度，失败后撤销未发布追加，而不能把暂存类型留给随后重新分析的路径。外部 context 的既有结果生命周期契约仍需保留。
