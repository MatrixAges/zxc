# 已解析名称缓存借用

## Intent：最终目标

作为完整原生接口分析迁移的第一阶段，消除每个名称/节点解析请求复制全部已解析名称和编号的开销，保留哈希查找与共享名义编号重映射。

## Data：可用证据

修改仅涉及三个生产文件：

- analysis/types.zig：resolved 使用标准库 StringArrayHashMapUnmanaged，键与值已有连续列，不新增自有容器或索引层。
- resolving/host/snapshot.zig：直接借用 keys() 与 values()，删除按 resolved.count() 分配两列以及遍历复制的循环。
- shared_types.zig：通过 values() 原位重映射编号，保持原映射含义。

本机 Zig 0.17.0 的标准库实现明确返回 backing keys/values，并允许修改 value 列；修改容器会使视图失效。TypeId 为 enum(u32)，借用前有 tag_type、size、alignment 的编译期检查，沿用本地 ID 表借用的指针转换方式，不逐项重新编码。

最终主构建 36/36 步通过。type-resolution、nominal-origins、native-declarations、semantic-cache 四项既有专项共 49/49 构建步、92/92 测试通过。未新增测试、未运行全量测试。

## Edges：边界与限制

借用发生于 generated.execute 之前；execute 同步读取 context.resolved，不修改宿主容器。它返回的 cache 是本次新增项，编号已读取为值。commit 的 ensureUnusedCapacity/put 和 shared remap 都在执行结束后发生，不将这次 borrowed view 留给下一次请求。

keys 的顺序从散列表迭代顺序变为插入顺序；查找以唯一名称匹配，顺序不是语言语义。seed 的 get/put、共享编号映射和已有诊断规则未改变。

此阶段只删除 resolved 的整列复制。aliases/visiting 的转换、已有类型列复制、共享 origins 合并和整个 analyzeView 的 RX/ZX 迁移仍未完成；计划中保留这些职责，不把复制移动到别处后宣称解决。

## Answer：交付与自我批判

交付三处最小存储与借用修改，英文提交并推送。该阶段不是整个原生接口分析的完成标志。

自审重点不是只检查分配次数减少，而是检查借用是否跨容器增长存活。当前同步执行、返回后提交的顺序满足边界；未来若将缓存写入移入执行期间或保留 Context，必须重新处理视图生命周期。别名列仍转换的事实已明确记录，不能把本阶段描述成所有 snapshot 全部零复制。
