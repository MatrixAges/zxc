# Store 独占区域回收参考

## Intent：最终目标

释放已被全部当前 Store 值替换的请求内存，避免可证明独占的更新随历史提交次数增长。保留无深拷贝、旧读取视图有效及每个 Call 独立提交的语义。

## Data：启用条件与使用

编译器检查入口和内部函数的 Store 写入。只有全部写入值都独占拥有其可变数据时，生成的 State 才声明 `can_release_retired = true`。该判定来自实际所有权检查，不依赖字段名、业务类型或输入大小。输入 IR 先经过完整校验，不能靠伪造函数返回权限取得此能力。

独占写入的例子是用标量计算和新列表构造完整下一状态；直接把旧 Store 的列表借入下一状态仍属于借用写入，不启用本阶段回收。详情见 [owned.zx](Store独占区域回收/示例/owned.zx) 和 [borrowed.zx](Store独占区域回收/示例/borrowed.zx)。不建议仅为了启用回收而无意义地复制业务数据。

HTTP Gateway 在每次请求结束、响应消费完成后自动执行清理。Zig 宿主保持显式控制：

```zig
{
    var request = state.request();

    defer request.deinit();

    const result = try request.execute(input);

    consumeResult(result);
}

state.releaseRetired();
```

调用清理时，所有 Request 及旧状态、ctx、输出的借用必须已经结束。需要继续保存旧快照的宿主不能在此时清理；不调用清理时保留原行为。

## Edges：边界与限制

- 请求输入以及宿主直接向 Request.commit 提交的数据，必须来自本次 Request arena、真正的应用长期存储或静态存储。若使用独占回收，不能把旧 Request 的保留区域视作永久应用内存，也不能把它的裸输出移交给新 Request 后就假定分配归属已经转移。
- Region 的 owner 标记表示当前 Object 来自哪个请求。清理后保留的不同 Region 数量不超过当前可写 Object 数量；单个区域仍包含该请求的其他临时数据，因此不是逐分配回收。
- 任一持久借用写入会关闭整个程序的这项能力。一般跨 Object 共享、精细分配回收与并发执行仍未完成。
- 非空直接 State.commit 没有请求来源证明，会永久关闭该 State 实例的清理。`can_release_retired` 表示编译期能力，不代表实例在手动提交后仍会释放。
- 一个 Call 失败不发布该 Call 的暂存值；后续 Call 失败不撤销此前成功提交，也不丢弃其内存所有权。
- 这项能力不增加 GC、引用计数、私有 Arena 布局访问或专用运行库。宿主需要兑现边界契约，编译器不能判断任意外部裸指针是否仍被使用。

## Answer：运行证据与成功标准

真实单 Object 应用在 1、10、100、1000 次独占更新后均保留 1 个区域，DebugAllocator 分配量为 604 字节；不执行清理时，1000 次后保留 1000 个区域、520084 字节。数值持续更新，列表内容保持正确，最终退出剩余分配为 0。

借用写入的 `can_release_retired` 为 false，调用清理仍保留原数据；直接 State.commit 后同样不释放。提交前失败没有发布，先成功提交再发生后续 Call 失败时，当前值仍更新，1000 次后仍只保留 1 个区域。

见 [实施计划](Store独占区域回收实施计划.md)、[区域观测](Store独占区域回收/区域回收观测.json)和[提交后失败观测](Store独占区域回收/提交后失败观测.json)。数字只代表这些真实应用，不是所有 Store 的固定内存预算。

自我复核：本阶段完成有静态独占证明且借用边界明确的区域回收，未完成全部共享 Store 的内存管理，未据此宣布自举前置条件全部满足。
