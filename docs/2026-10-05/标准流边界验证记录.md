# 标准流边界验证记录

## Intent：最终目标

第 391 部分覆盖 std:process 六个同步标准流接口，分别验证直接原生实现和真实 ZX/RX 应用中的组合行为。

## Data：可用证据

新增 `test-process-stdio`，接入 `test-standard-resources` 和总 test。直接接口夹具覆盖 std.Io.operate：仅接受 stdin 读取、stdout/stderr 写入；强制短读/短写、EOF、IO 失败、取消，并禁止 API 关闭标准句柄。没有读取用户终端。

| 层次             | 数量 | 覆盖                                                                                                                                         |
| ---------------- | ---: | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 直接读取         |   25 | 空流、零上限、恰好与超限、NUL/非法字节、UTF-8、跨缓冲、最大 u64、结果独立所有权、EOF 后再读、IO 失败/取消/恢复、成功及失败路径的全部分配失败 |
| 直接写入         |   24 | 四个写入接口的空流、短写、失败前后恢复、二进制保真、六类非法 UTF-8 在 IO 前拒绝、跨缓冲、流隔离、顺序追加与取消                              |
| 真实读取应用     |   22 | 原始管道输入与 JSON 参数分离、精确字节上限、4096 边界、16385 字节内容、六类非法 UTF-8 及字节/文本输出                                        |
| 真实 RX 双流应用 |   28 | byte/text × json/discard，空输入、Unicode/NUL、全 256 字节集合、大输入、错误传播、额外 argv 拒绝、真实文件重定向追加                         |
| 合计             |   99 | 两种优化模式不重复计数                                                                                                                       |

每条真实应用通过 CLI 构建并启动独立子进程。读取例子返回数据；RX 例子顺序调用读取、stdout 写入和 stderr 写入，遵循 ZX 不支持普通副作用表达式语句的契约。输出用 Node Buffer 做逐字节精确比较。

## Edges：边界与限制

IO 替身验证内部接口，不证明所有平台或所有 OS 设备行为。真实管道及文件重定向只在当前宿主执行；没有建立交互式流或并发写入原子性保证。超过上限的输入可能已被部分消费，测试不要求其可无损重读。

直接 IO 错误经 Reader/Writer 表现为 ReadFailed/WriteFailed，本部分不要求恢复底层错误名称。text 的最大字节数按 UTF-8 字节计数，不能按字符数量放宽。

CLI 现有默认 JSON 写出使用 Zig Stringify：合法 UTF-8 的 u8 切片是 JSON 字符串，否则是数字数组。测试按该既有契约使用 Node 的独立 UTF-8 校验作预期分类。二进制 API 的保真以原始 stdout/stderr 和直接读取断言为准，不依赖 JSON 表示稳定性。

## Answer：结果与交付

Debug 与 ReleaseSafe 均通过：每种模式 49/49 直接接口检查、50 项真实应用检查，17/17 构建步骤成功；两个执行进程最终退出码均为 0。运行日志、执行记录 JSON、测试草稿位于标准流边界验证目录；正式测试位于 packages/test/tests/standard/resources/stdio 与 packages/test/tests/runtime/stdio，构建入口为 packages/test/build/process_stdio.zig。IDEA 计划包含架构与数据流 Mermaid 图。

## 自我批判与过程修正

1. 最初从 allocRemaining 的简短注释推测 `max_bytes + 1` 可能放宽上限，真实边界检查推翻该推测。进一步核对 appendRemaining 实现及文档，它在达到限制时直接报错，故 +1 正是允许恰好 max_bytes 的实现方式；没有报告不存在的生产缺陷。
2. 首个 JSON 预期错误地把所有 u8[] 都视为数字数组；已根据现有 runner 和 Zig Stringify 契约修正，原始字节比较独立保留。
3. 初版双流例子使用 ZX 中不合法的普通副作用语句；已改为 RX 编排三个单职责函数，没有为通过测试修改语言规则。
4. 不把多个 UTF-8 子样本或每个 OOM 注入点重复算作新的测试声明。49 项直接检查和 50 项实际子进程场景分开记录。
5. 当前没有发现本部分生产缺陷，没有向实现会话发送无问题消息，也没有修改生产源码。
