# 开发热重载参考

## Intent：用途

开发时自动构建并运行本机原生应用。源码或依赖变化后，成功构建会重启应用；编译失败时，旧应用继续运行。

## Data：命令

```sh
zxc build main.gateway.rx --out build/server --watch --run

zxc build main.zx --out build/app --watch --run -- '{"value": 41}'
```

`--` 后的内容全部是应用参数，保留空格和特殊字符，不经过 shell。ZX/RX 的输入 JSON 仍按原应用入口约定传递。使用显式 `std:process` 参数的程序可接收多个参数。

| 选项或情况                   | 行为                                       |
| ---------------------------- | ------------------------------------------ |
| `--watch`                    | 只观察和构建，不启动应用                   |
| `--watch --run`              | 首次成功构建后启动，后续成功构建后重启     |
| 编译失败                     | 报告诊断，保留旧运行实例                   |
| 应用正常退出或崩溃           | 报告退出结果，继续观察；不反复启动同一产物 |
| 运行副本准备失败             | 报告错误，旧实例仍在                       |
| 旧实例已停止但新实例启动失败 | 报告错误，等待下一次输入变化               |
| Ctrl+C / POSIX SIGTERM       | 结束观察，清理受管应用并退出               |

## Edges：运行边界

只支持 `build` 的本机原生 `app`、`process` 宿主，并且必须同时指定 `--watch`。`--mode lib`、`--host node`、显式 `--target` 和单独 `--run` 都会被拒绝。Node 插件或 WASM 应用由各自宿主管理加载。

这是进程重启：新实例重新执行初始化，内存 Store 不会迁移。切换期间有短暂停机，也不会等待正在处理的业务请求全部完成。需要保持状态或零停机发布时，应由应用部署层承担该契约。

应用继承当前工作目录、环境、stdout 和 stderr。stdin 关闭，读取会得到 EOF；这不是交互式终端作业管理器。每次运行使用与输出文件同目录的唯一副本，保留执行权限及相邻资源目录，避免运行中的 EXE 阻止 Windows 发布新文件。应用看到的可执行文件路径是该副本路径。正常退出、重建和终止观察时删除副本。

macOS/Linux 使用独立进程组，先发送 TERM，最多等待约 500ms，然后发送 KILL 并回收根进程。根进程先退出时也会清理受管组中的后代。Windows 使用带 KILL_ON_JOB_CLOSE 的 Job Object；子进程先挂起、加入 Job 后才恢复执行，重启时关闭 Job 并等待根进程结束。

主动脱离进程组、改变身份以失去信号权限的后代不在 POSIX 管理契约内。SIGKILL、崩溃或断电无法运行 POSIX 清理代码，可能留下运行副本。Windows 关闭控制台时由操作系统关闭 Job handle；未声称所有强制退出竞态都已消除。

## Answer：示例与证据

仓库内的已有 Gateway 示例可以直接体验：

```sh
zxc build docs/2026-10-05/开发热重载/应用/main.gateway.rx \
  --out build/reload_server --watch --run
```

另一个终端发送请求：

```sh
curl -X POST -H 'Content-Type: application/json' --data '5' \
  http://127.0.0.1:19847/api/v1/echo
```

修改同目录 `echo.zx` 的返回表达式即可观察新响应。实际验证覆盖响应从 5 到 6、编译失败时继续返回 6、修复后变为 7，以及进程身份变化和副本清理。原样参数传递、自然退出、忽略 TERM 的后代清理也已实跑。Windows/Linux 已完成交叉构建，运行行为证据来自 macOS，见 [实施与验证记录](开发热重载实施计划.md)。
