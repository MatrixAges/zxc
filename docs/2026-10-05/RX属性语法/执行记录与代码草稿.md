## Answer：代码草稿与后续接入

### 最小属性类别

建议在共享 Attribute 中增加语法类别。默认值仅用于维持标准 XML AST 的字符串性质，绝不能令 RX 分析继续把默认字符串解释成代码。

```zig
pub const ValueKind = enum {
    string,
    expression,
};

pub const Attribute = struct {
    name: []const u8,
    value: []const u8,
    location: Location,
    value_location: Location,
    raw_value: ?[]const u8 = null,
    value_kind: ValueKind = .string,
};
```

`string` 的 value 为已解码内容，raw_value 保留原文。`expression` 的 value 与 raw_value 均为不含外层花括号的 ZX 原文。value_location 指向外层分隔符之后，保留前导空白，避免 trim 后偏移失真。

类型表达式不新增第三种词法类别：`type={u32}` 仍为 expression，由属性契约指定类型上下文。

### 表达式消费者接入草图

```zig
const expression = switch (attribute.value_kind) {
    .string => try buildStringLiteral(allocator, attribute),
    .expression => try parseZxExpression(allocator, attribute),
};

return analyzeExpression(allocator, expression, options);
```

上面三个函数名表达拟定职责，并非仓库已有 API。字符串分支应直接构造现有 ZX 字符串节点；避免再拼接引号、重新解析合成源码并维护额外转义偏移表。

接入点至少包括 `analysis/expression.zig`、`analysis/project/constraints.zig`、`analysis/store/call.zig`，以及 Case 标签匹配与 Store 初值。不能只更新公共 compile 而遗漏项目推导。

### 解析边界要求

- 不能用第一个右花括号作为结束位置。
- 对象嵌套、字符串中的花括号、注释和模板插值按 ZX 词法识别。
- `<`、`>`、`&` 在花括号内是 ZX 源码，不要求 XML 转义。
- 空表达式与只有注释的表达式拒绝；空字符串保留。
- 不能把整个 RX 剩余文本直接交给当前完整 ZX lexer：它会继续读取表达式后的标签。需要有界或可暂停的词法入口。
- 新 RX 入口使用真实源码生成 AST；禁止转换成合成 XML 后冒充原源码位置。

### 诊断与 API 迁移

字符串使用实体解码映射；表达式按保留的原文字节定位，行列计算仍正确处理 CRLF。开始位置与结束位置分别处理，不能仅给所有 span 加固定列偏移。

建议新入口命名为 `rx.parse`；`dsl.parseXml` 继续表示标准 XML。现有 `rx.parseXml` 的删除或弃用需与公开 API 策略一起处理，不能把支持非 XML 的新解析器悄悄挂在旧名称下。`parseModules` 与 CLI 装载必须统一采用 RX 新入口。
