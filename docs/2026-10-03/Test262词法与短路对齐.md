# Test262 词法与短路对齐

## Intent：最终目标

在现有 2,450 个除法执行案例之外，增加不同职责的覆盖：词法失败必须在解析入口发现；语义失败必须先证明解析成功；短路必须通过危险分支是否执行进行验证。继续保留 ZX/RX 设计。

## Data：可用证据

- 续接时根回归仍为 2,836/2,836，通过。
- 现有 CLI 中，`return 1__0` 的 Output 为 f64 时得到 lexical，为 bool 时得到 type_mismatch；`return 1e+` 得到 type_mismatch。
- `frontend/lex.zig` 数值扫描没有校验分隔符和指数完整性；`analysis/numbers.zig` 在检查目标类型后才检查分隔符。因此同一非法 token 的诊断类别依赖后续类型上下文。
- 成熟样例 `compiler/tests/helpers.zig` 已采用“分析负例先解析成功”的分层方式。
- 固定 Test262 源码可用于逐项检查 numeric separator 与逻辑/空值短路语义；记录必须指向具体文件。

## Edges：边界与限制

- 不顺手引入 `.1`、`1.`、十六进制或 JS 隐式类型转换。
- 本次修复只处理已扫描为 number 的 token 内部词法合法性。合法数值的范围、精度和类型错误仍属于 analyze 阶段。
- 运行负例区分正常返回 error 与安全检查 panic，不能把任意非零退出当作成功。
- 短路用例同时覆盖跳过和执行分支；只有“没有报错”的单向测试不足以证明分支正确。
- 稳定输入案例数、源码模板数和上游已审查数分别统计。

## Answer：执行与成功标准

1. 新增阶段与位置断言支持，保存词法正负目录。
2. 在修复前运行，确认指定案例因错误阶段/位置失败。
3. 最小移动词法检查并补指数完整性校验，相关及根回归通过。
4. 建立短路与条件分支执行目录，包括精确 IndexOutOfBounds 预期。
5. 扩展上游逐项映射，写入实际运行结果与下一步。

```mermaid
flowchart LR
    S[源代码目录] --> L[parse 内词法与语法]
    L --> N[指定类别与位置断言]
    L --> A[analyze]
    A --> T[类型或所有权诊断断言]
    A --> G[生成 Zig 并执行]
    G --> R[值或精确运行错误断言]
```

## 执行记录

### 词法缺陷与修复

修复前，在 `packages/test` 执行 `zig build test-frontend --summary all`：256 个非法 token 案例全部失败，10 个合法数值通过。失败原因是 parse 没有返回诊断，符合前期复现。

将分隔符检查从 `analysis/numbers.zig` 移入 `frontend/lex.zig` 的数值扫描结束处，增加指数末尾必须为数字的检查。原先 256 个负例均在 parse 返回 lexical，且位置完全一致；10 个合法形式继续通过。随后加入上游原始 token 的 8 个补充回归，当前词法负例为 264 个。

`1e+`、`1__0` 不再取决于输出是 f64、u64 或 bool；模板插值中的绝对位置也经过验证。范围与精度仍由 analyze 检查，没有扩大数字语法。

### 类型与短路

- 12 种类型（8 数值、bool、string、列表、对象）两两组合，覆盖 13 种操作符，共 1,872 份源代码。正例先 parse、analyze 再 validateIr；负例必须 parse 成功后返回 type_mismatch。
- 7 份 ZX 短路/条件程序，460 个具名输入。覆盖 `&&`、`||`、嵌套优先级、三元两支、optional 空值回退；列表为空、越界和 u64 最大索引均有对应输入。
- 被跳过的危险分支不得返回错误；被选择的危险分支必须精确返回 IndexOutOfBounds。没有把任意运行失败当作通过。

### 第二个真实缺陷：有符号余数的机器异常

第一版独立进程集合共 80 个案例，其中 i32/i64 最小值对 -1 求余意外终止，退出 -6，stderr 为 Arithmetic exception。生成代码位置是直接 `@rem(left, right)`。框架拒绝这种意外终止，没有把它当作预期安全检查。

依据现有 ZX 余数契约及 [Zig 0.16 @rem 语义](https://ziglang.org/documentation/0.16.0/#rem)，该运算余数可表示为 0；它与最小值除以 -1 导致的商溢出不同。

后端将有符号余数降为 `runtime.signedRemainder`：操作数符号扩展一位，计算 @rem 后收束结果。实现没有检查某个测试输入，而是对所有有符号余数采用同一数值算法。helper 明确启用 runtime safety，零除数仍被检查；除法仍沿用原有溢出行为。

原先 80 个案例全部通过后，补充 13 个有符号边界值的两两组合，并按运算/左右输入去重。目前共 408 个独立进程案例，Debug、ReleaseSafe、ReleaseFast 均通过。

### 上游映射与构建完整性

- 新增 11 项 numeric-separator 上游审查：5 个解析负例、6 个执行正例。原始 token 与全部正例数值断言均保留，共关联 25 个本地案例。
- 正例中的 15 个数值通过两份 ZX 程序真正生成执行；不能用 parse 成功关闭这些条目。
- 当前累计 21 个上游文件已审查（10 equivalent、11 adapted），53,576 个未审查。短路目录尚未逐项关闭上游条目，不能由本地 460 个通过反推映射完成。
- `suites.json` 同时驱动 Zig 构建和矩阵审计，防止出现孤立目录、多重登记和缺失目录。辅助字符串编码文件也登记为生成步骤的输入，修改后不会沿用旧生成缓存。
- 前端目录统一编译为一个测试程序，继续保留 2,146 个独立 test 名称；避免每个操作符目录都重复优化整个编译器。

### 对测试框架的反证

1. 将除零预期错误地设置为 integer overflow，子进程确实报 division by zero；执行器返回失败。仅非零退出码不足以判绿。
2. 在临时副本增加未登记 JSONL，矩阵审计拒绝。没有向正式测试目录留下探针。
3. 所有隔离报告逐一核对案例 ID 集合、条目数和 passed 字段，三个模式均为 408/408。

## 自我批判与续接

当前新增案例 5,479，还需至少 24,522 个不同有效案例才超过 30,000。不能通过重复优化模式计数补齐差额。

测试驱动修复已产生两项真实改进，但这些结果不能证明完整语言成熟：字符串字节行为、集合边界、所有权分支、模块图、RX、Store 宿主和资源失败仍是后续重点。当前只验证本机平台；加宽余数的性能没有基准数据，不能声称没有成本。

下一批优先补集合/所有权与字符串行为，继续建立上游逐项证据。已支持的短路表达式仍需把上游各文件的适用与不适用断言分别审查，不能批量关闭目录。
