## 第一性边界

256 的含义是同时活动的命名声明数，即 visiting.count；不能用语法嵌套或工作帧数量代替。builtin、resolved、imported alias 在深度检查之前；同名 visiting 的 Recursive 也优先于 Depth，满表的 Depth 则优先于 Unknown。

普通 analyze 会创建自己的 maps，无法观察调用前已有标记。直接测试正式 frontend.types 可验证这些顺序与标记所有权。设置多重命中的 maps 是低层优先级输入：使用合法 Scalar ID 区分结果，不通过普通 initialize 伪装为可导入 builtin 的应用程序。

新状态机使用显式工作栈并创建新的失败点。成功和失败均应撤销当前调用已进入的名字，不清空调用前已有 visiting。成功内层声明可以留下 resolved 缓存；外层后续失败不意味着整张表要回滚。

## 名称与精确深度

完整 Scalar 名字以及 number/boolean 同义词均返回明确的标准 ID，不追加类型行。预存 resolved/alias 的 void ID 0 在满表及同名 visiting 前仍为有效命中，验证桥接的 ID+1 表达没有把零值当 miss。

255 和 256 条 Native AST 前向别名末端接 u64 均成功；257 条在第 257 个引用处精确返回 Depth。255 条末端接 Missing 报 Unknown，256 条末端接 Missing 先报 Depth。相同 255/256/257 的浅语法别名还通过真实 indexed Program 再验证一次，避免把低层构造与实际 Parser 输入混为一谈。

一个命名声明包裹 300 层 optional 成功，完整图为 11 个 Scalar 加 300 个容器。这观察命名深度与工作帧数量不同，而不是给语法解析器强加无限嵌套要求。

外层 Root 对象先完成 Child = u64[]，随后在 Missing 处失败：Child 的缓存保留，Root 的标记退出，预存 Held 与 Cached 保留。第二次请求仍报告相同 Unknown，而不是 Recursive；已经完成的 Child ID 和表行数保持。纯递归、未知链以及名额只剩一个时的成功也分别检查准确集合。

## 节点和诊断先后

直接 Native AST 检查正式节点语义：不支持的 Map 应先拒绝应用名，不能先解析 Missing 参数；重复字段先拒绝第二个字段名，不能先解析其类型。tuple/object 会先完成全部子类型，再检查 task，因此后面的 Missing 优先于前面已解析的 Work task 容器错误。Work 用正式 types.errorSet/task 创建，先保证类型表合法。

optional<void>、空 tuple、空 object 合法；list<void> 与 object void 字段有各自诊断。匿名 enum 与空声明 enum 的错误来源、span 不同。重复 enum 成员使用后一个成员 span，成员保持源顺序，同形但不同名字的 enum 不做结构合并。直接 native opaque 产生 Node，引用它的普通 alias 复用 Node；普通声明或容器中的 opaque 仍 Unknown。

字段排序与同形结构驻留、Array 应用与 list 语法复用也有独立预期。所有诊断断言同时比较 code、message、start/end，不仅检查任意失败。

## 四来源真实运行

- Native AST：frontend.parse 产生正规 AST，再 frontend.analyze；完整图按照手写预期检查。
- Program：parseModule 的 indexed 分支和 analyzeModule；同一源码使用同一独立结构预期，不把 Native 输出当 oracle。
- Expression：parseExpressionInput 的 indexed 分支，通过 loop next 语句块里的 const 类型注解触发类型 Reader。检查实际 row/entry 符号类型；两个错误注解强制观察 Generic/DuplicateField 的精确 span。
- Native interface：真实 project.analyze 导入 host.d.zx，检查同一容器和 enum 图、resolution@1 描述符以及直接 opaque Node。

这四条正向来源均检查完整 validateIr。只编译普通字面量不能证明 Expression 类型读取器被调用；本轮显式保留带 annotation 的源码和语义错误观察。没有为测试新增生产导出，也没有复制加载另一份 frontend。

## OOM 的正确观察范围

Native AST 输入、Scalar 前缀、三份既有 Held 标记和已有缓存先在稳定地址的 caller Arena 中准备。把失败包装器放在 Arena 的 allocator 外侧，并禁止 resize/remap，可按解析 API 每次 alloc 注入失败，而不是仅按 Arena 新 backing block 分配。

先执行不失败基线，得到实际分配调用数，再遍历每个 fail_index。Scalar 单别名、32 层别名、完整混合声明初始化、12 层 Unknown 拒绝路径均观察真实 OutOfMemory，既有标记/缓存保留、本次标记退出；关闭故障注入后重试。Scalar 场景的最后一次分配是 cacheResult 的首次 resolved.put：已有 visiting 容量足够，Scalar 不分配新的类型行，cache put 后只 leave/pop/deinit；测试用动态基线的末端索引，未固定 malloc 编号。

TypeStorage 的完整合法前缀与结构也在 OOM 后检查。混合场景允许已经完成的类型或缓存保留，retry 使用相同声明得到独立图预期，没有要求类型总行数恢复至调用前。

Arena 统一回收持久字段、成员、临时 tuple/object 缓冲区；这些低层 API 本来不是独立堆分配器的完整 Result owner。手工逐点扫描不会误用 checkAllAllocationFailures 的逐对象 free 账本来要求不成立的契约。std.testing.allocator 仍检查最终 owner 的物理内存释放。
