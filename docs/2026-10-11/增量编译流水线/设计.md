# 增量编译流水线设计

## Intent：最终目标

建立 ZX/RX → IR → Zig → LLVM 目标文件的全链路增量编译，zxc 自举与用户应用都能受益：

- 只改一个函数体时，ZX/RX→Zig 只做与改动成比例的工作，目标为毫秒级。
- Zig→LLVM 只重编受影响的部分，并且可以并行。
- Release 产物保持单编译单元，性能不受影响，也不引入运行库。

用户原话见 [user_request.md](../../user_request.md)（2026-10-11 20:05 之后的三条）。

## Data：现状测量

本机 i9-13900KF，32 线程；仓库根执行 `zig build -Doptimize=debug`：

| 改动          | 总耗时 | 关键路径                                           |
| ------------- | -----: | -------------------------------------------------- |
| 改 1 个 ZX    |  43 秒 | 生成器运行 21 秒 → zxc 编译 20 秒                  |
| 改编译器 Zig  |  61 秒 | 种子生成器编译 18 秒 → 运行 20 秒 → zxc 编译 21 秒 |
| ZX + `stage0` |  32 秒 | ReleaseFast 生成器 11 秒 → zxc 编译 20 秒          |

- **生成器（ReleaseFast，函数缓存全命中）：** infer 1.3 秒，emit 7.7 秒。emit 的缓存键包含全程序分析结果，所以先跑完整个后端分析才能查缓存。
- **zxc 的 Debug 编译：** 约 13 秒花在 LLVM 代码生成和位码重解析上，源头是 82.6 MB 生成代码（1,489 个函数文件）。
- **单次 Zig 调用：** 固定开销约 1.2 秒。Zig 0.17 的增量编译只支持自带后端，而自带后端在本机 macOS 链接失败（见 [宿主后端构建试验](../完整自举接续/宿主后端构建试验.md)），因此 Zig→LLVM 达不到毫秒级。
- **命名稳定性：** 函数文件名只由源路径决定，改函数体时不变；类型名由内容决定，并集中在一个 `types.zig` 中。

## Edges：边界与约束

- 遵守零运行时：分区之间只是普通静态链接的目标文件。跨区调用由编译期生成的转发函数完成，不加动态调度或解释层。
- Release（`fast`/`safe`/`small`）默认仍为单编译单元，保留跨函数内联。分区只在 Debug 默认开启，也可以显式选择。
- 后端缓存键的重设计与 genz 后端重设计（另一会话）会改到同一处，须在其降级改造落地后一起做，避免两边同时改。
- 不新增测试，不跑全量测试，不触发 CI。

## Answer：分阶段方案

```mermaid
flowchart LR
    S[ZX/RX 源文件] -->|内容摘要| F[前端：模块级产物缓存<br/>接口未变即截断]
    F -->|函数 IR| B[后端：函数 Merkle 键<br/>先查缓存再分析]
    B -->|只写变化的文件| O[稳定目录]
    O --> P1[分区 1 目标文件]
    O --> P2[分区 2 目标文件]
    O --> Pn[分区 N 目标文件]
    P1 & P2 & Pn --> L[链接]
```

1. **Zig→LLVM 分区（先做，收益最大）**
    - 生成器把函数文件按 `hash(函数名) mod N` 分到 N 个固定分区，每个分区编成一个独立目标文件。
    - 分区内的调用照常通过 `@import` 互相引用。调用其他分区的函数时，导入的是同名桩文件：桩文件只保留函数签名，再用 `bridge.import` 转发到对方导出的 C ABI 符号。参数元组和返回值都按指针传递，错误按错误集中的序号传递。
    - 每个分区只导出被其他分区或外层门面实际引用的函数变体。
    - 原型已验证三点：桩文件只反射签名，不编译函数体；目标文件里同一个函数只有一份实现；返回值和错误都能正确跨单元传递。
2. **稳定输出路径**
    - Zig 的缓存键包含源文件路径。生成器改为写入固定的持久目录，内容不变的文件不重写，Run 步骤只输出一个戳文件。
    - 这样未变的分区直接命中 Zig 缓存。
3. **宿主也变成目标文件**
    - 手写编译器与门面单独编成一个目标文件，最终的可执行文件只剩极小的入口加链接。
    - 这样改动任何一个分区，都不会再触发手写代码重编。
4. **后端函数缓存**
    - 键由函数 IR、类型形状和被调函数的摘要键共同组成，自底向上计算。调用方提出的需求（wanted）单独作为输入并入键。
    - 缓存命中时跳过分析。这一步在 genz 唯一性降级改造完成后和它一起做。
5. **前端模块缓存**
    - 复用 `semantic_cache` 的 `Artifact.Module`：键为源文件摘要加依赖接口摘要。
    - 重新分析后如果接口摘要不变，下游模块保持干净，这就是提前截断。
6. **用户应用**
    - `zxc build` 的 Debug 模式使用同一套分区与缓存。

成功标准：改一个函数体后重建，前三步完成时进入秒级（单个分区编译加一次链接，约 3 秒），第 4–5 步完成后，生成器部分降到毫秒级。产物与单编译单元的生成结果在语义上一致。

## 实施记录：第 1–3 步

仓库根目录执行 `zig build -Doptimize=debug` 时默认使用 64 个分区；`-Dgenerated-partitions=0` 恢复为单编译单元。`compiler` 和 `cli` 包单独构建时默认为 0，所以 `packages/test` 等使用方的行为保持不变。

| 改动后重建 |    总耗时 | 关键路径                                               |
| ---------- | --------: | ------------------------------------------------------ |
| 改 1 个 ZX | 约 9.2 秒 | 生成器 5.9 秒 → 1 个分区 1–2 秒 → 链接 0.3 秒          |
| 冷构建     |  65–70 秒 | 生成器 12–15 秒 → 分区并行 → 宿主目标文件 14 秒 → 链接 |
| 无改动     |    0.4 秒 | 只有构建配置与缓存检查                                 |

改动前，同样改 1 个 ZX 需要 43 秒。

分区数的取舍：32 个分区时，改动后重编单个分区约 3 秒，链接约 2 秒；64 个分区时分别约 1 秒和 3 秒，总计少约 1.5 秒。生成器输出不变时，64 个分区全部重编约 34 秒（32 线程）。

### 实现时发现的约束

- **内联函数不能跨分区转发。** `pub inline fn`（741 个 `callValue` 等）会复制进每个调用方所在的作用域，并按传递关系一并复制，和单编译单元的展开方式一致。
- **分区目标文件必须保留调试信息。** 去掉调试信息的分区链接后，zxc 运行时会在 `ArenaAllocator.loadFirstNode` 读地址 0x20 时崩溃；同样的分区保留调试信息后，产物与单编译单元一致。
- **错误码在每个编译单元内单独编号。** 所以经函数指针跨单元返回的错误（例如 `std.Io` 的 vtable）会错位。宿主目标文件因此在自己的单元内构建分配器、`Io.Threaded`、环境表和预打开目录，可执行文件入口只传入 `std.process.Init.Minimal`。分区之间的错误则按错误集中的序号传递，不受影响。
- **目标文件会传给模块图中的每一次编译。** Zig 编译某个目标文件时，会把它模块图中挂着的全部链接对象都作为输入，于是任何分区一变，宿主目标文件就要重编。因此分区对象不再挂在 `generated` 上，而是挂在单独的 `generated_objects` 模块上，只由最终产物导入。
- **缓存标识要放在入口单元。** `cache_identity` 覆盖全部编译器源码，每次改 ZX 都会变。它改为由可执行文件入口导出 `zxc_cache_identity` 符号，宿主通过 `@extern` 读取，因此宿主目标文件不随之重编。

### 链接

- **改用平台链接器：** Zig 0.17 自带的 Mach-O 链接器处理 64 个分区加宿主目标文件（约 440 MB）需要约 3 秒。在 macOS 上为本机构建时，最终链接改由 `xcrun clang` 驱动 Apple `ld` 完成，同样的输入只需约 0.3 秒；该工具不可用或在其他平台上时，仍用 Zig 链接。
    - 入口单元编成静态库 `zxc_start`，内含 compiler_rt 与 UBSan 运行时（Debug 下 libyaml 的 C 代码要用），对应 Zig 链接可执行文件时自动加入的运行库。
    - 主线程栈大小保持 16 MiB。
    - 根目录构建通过 cli 的命名路径 `zxc` 安装可执行文件。
- **调试信息：**
    - Zig 链接器把宿主目标文件的调试映射项写成了 `N_SO`，应为 `N_OSO`。
    - libyaml 挂在宿主模块上时，Zig 会把它并进宿主目标文件重新生成，这一步丢掉了全部 DWARF。

    两者都会让报错堆栈只显示 `???`。现在 libyaml 只由最终产物链接，宿主目标文件保留调试信息，报错堆栈恢复了源码位置。

- **安装时的 RX 测试：** `zig build` 安装时只检查 RX 测试能否编译，不再生成并链接测试二进制（原先每次改动都要再花 3 秒链接）；`zig build test` 不受影响。
- **代码体积：** 每个分区各自实例化 std 泛型与公共辅助代码，分区构建的 `__TEXT` 为 238 MB，单编译单元为 89 MB。

### 验证

- `packages/cli/tests/runtime/cases` 下全部 29 个用例：分区版 zxc 的输出与日志，和单编译单元 Debug zxc 逐字节一致（`store` 用例在两者中都以相同信息失败）。
- 改 1 个 ZX 后重建，只有 `part_24` 中的一个文件和 `.zxc-inputs` 被改写，只重编了 `zxc_partition_24`，宿主目标文件命中缓存。

### 未满足项

- **生成器仍需约 5.9 秒：** infer 0.66 秒，emit 4.8 秒，写出 0.36 秒。
    - Debug 构建的生成器从 ReleaseSafe 改为 ReleaseFast。它的编译时间不变（17 秒对 18 秒），缓存命中时 emit 从 7.1 秒降到 4.8 秒，生成结果逐字节相同。默认的 safe 构建仍使用带检查的生成器。要降到毫秒级，需要完成第 4–5 步。
    - infer 原为 2.93 秒，其中逐模块的 mixed 编译占 2.55 秒。1,500 个模块每个都要处理整张共享类型表（2,850 个类型）：分析前校验一遍（253 毫秒），连同全部名字字符串深拷贝一遍（307 毫秒），链接时再校验一遍。
    - 共享表只来自项目自己分析并链接的模块，生命周期长于每次分析，所以现在 resolved 模式只复制列、借用字符串。扩展已有表（`first` > 0）时，也只在 internal 构建中重新校验。改后 infer 为 1.65 秒，生成结果逐字节不变。
    - RX 流程里的 1,083 个属性表达式也有同样的问题：每个都要校验一次共享表（181 毫秒），再深拷贝一次（327 毫秒），而真正的分析只占约 20 毫秒。表达式选项新增 `borrow_types`，RX 流程编译时打开，结果直接借用共享表的字符串。之后 infer 降到 1.1 秒，生成结果仍逐字节不变。
    - RX 类型推断的不动点循环原先在每轮重建赋值等价类后只合一一对节点，随即从头再来，共重建 604 次，耗时 367 毫秒。现在一轮内合一全部候选对；若某个代表节点的载荷在本轮已经变化，就留到下一轮用新建的等价类处理。改后约 5 毫秒，infer 降到 0.77 秒。生成结果逐字节不变，40 个 RX 测试源与旧版 zxc 的输出和退出码一致（其中 1 个只是两边都因缺少 z3 失败，堆栈格式不同）。
    - 写出原先需要 1.9 秒，其中 1.6 秒花在把 6,199 个文件逐个读回比较上。现在改为在输出目录记录 `.zxc-files` 内容摘要清单，只比较摘要；陈旧文件也按清单删除，不再遍历目录。
    - 函数缓存全部命中时，emit 的 7.2 秒几乎都花在 genz 唯一性分析上（`sample` 显示 `zx.uniqueness.*` 占绝大多数样本）：它对每个函数都先分析，再查缓存。后续处理见下文“genz 唯一性分析与自托管后端”。
- **生成器自身变化会让函数缓存全部失效：** 缓存键包含生成器二进制的摘要，所以改编译器 Zig 代码后，全部函数都要重新生成。不过生成结果不变的文件不会重写，分区对象仍能命中 Zig 缓存。
- **infer 的并行与缓存：** `appendBody` 要求分析时的函数基表就是当前共享表，所以按依赖分层并行分析时，需要把局部函数号重映射后再链接。这样最多能省约 1.1 秒。若要做到模块级缓存，还需要把 `semantic_cache` 的 `Artifact.Module` 接入 RX/ZX 混合路径；目前该缓存只用于纯 ZX 的项目分析。
- **配置阶段：** `cache_identity` 在构建配置阶段读取全部编译器源码来计算摘要，这部分开销仍在。
- **用户应用（第 6 步）：** 测量后暂缓，小应用分区没有收益。用 `packages/cli/examples/quote.zx` 测（Debug 版 zxc）：
    - 改函数体后，`zxc quote.zx --out` 生成 Zig 只需 22 毫秒，ZX→Zig 已经是毫秒级。
    - `zxc build --optimize Debug` 总计 1.6 秒，几乎都是单次 `zig build-exe` 的固定开销；首次冷构建 12.5 秒，主要是标准库与 compiler_rt。
    - 应用规模大到单个 Zig 编译单元超过数秒时，再把分区方案用到 `cli/src/cli/build.zig` 的 `build-obj` 多进程调用上。

## 实施记录：genz 唯一性分析与自托管后端

genz 会话停止后由本会话接手，提交为 `a49a02757`。新的唯一性分析让改 1 个 ZX 后的重建变为 12.5 秒，其中 emit 9 秒。

### 唯一性分析

计时插桩显示，emit 的 8.1 秒在 `Uniqueness.analyze`：外层 3 轮，每轮从最乐观状态重新 settle（约 5,300–6,250 次函数体分析）再做 demand。生成器根模块为 ReleaseSmall 时默认去掉符号，采样前需临时关闭 strip。改动如下，生成结果均逐字节不变：

- `sites.linear` 只取决于函数体和固定的 callee hold/mutate 类型，原先却在每次分析前清空 memo。现在 memo 跨分析保留，并和逐槽 `levels` 一样改为按根槽位偏移索引的稠密表，不再用 `u64` 哈希表。
- `Slots` 预先算好 unwrap 结果和成员类型；每个函数体的表达式行只读取一次，各遍只遍历调用和列表更新。
- slot 布局与 holds/mutates 合成全程序共享的 `Basis`，只建一次。50 个导出入口的 reentry 从 305 毫秒降到 10 毫秒。

结果：analysis 从 8.1 秒降到 0.9 秒；缓存命中时 emit 从约 9 秒降到 1.24 秒。

**顺序依赖：** 把 settle 的 FIFO 工作队列换成“先取最小序号”或“先取最大序号”后，生成结果都会变化（4 个和 13 个文件不同），所以这个不动点并不与求值顺序无关。可能的原因是：递归函数分析时，`arguments` 会改写它自己正在读取的 input summary。目前保持原 FIFO 顺序；要做并行或增量的唯一性分析，得先消除这种顺序依赖。

### 自托管后端

单个分区经 LLVM 编译需约 1.5 秒，几乎全是固定开销；分区数增至 256 时仍需 1 秒，链接还会变慢。x86_64 Debug 下改用 Zig 自带后端（`use_llvm = false`）后，单个分区只需 0.4 秒，全部 64 个分区约 11 秒。约束如下：

- 调用分区的代码必须出自同一后端。LLVM 编译的宿主调用自托管分区时，会在 `ArenaAllocator.alloc` 处因对齐错误崩溃，因为 Zig 自有类型的布局只在同一后端内一致。宿主目标文件因此也改用自托管后端。
- 入口静态库 `zxc_start` 保持 LLVM：它只导出 C 符号，而 Apple `ld` 无法读取自托管后端生成的归档文件。
- Zig 0.17 的 Mach-O 链接器链接自托管目标文件得到的可执行文件，运行时会被内核终止（退出码 137）。因此只有能用平台链接器时，zxc 本体才选用自托管分区，同时传入 `-Wl,-w`，去掉逐个指针报告的未对齐警告（ld 会自动退回非 chained fixups）。
- compiler 包同时提供两套分区对象：`generated_objects`（LLVM）供测试和生成器使用；`generated_objects_self_hosted` 供 zxc 本体使用。Zig 只构建被依赖的步骤，所以没用到的那套不会编译。
- 安装时的 `rx-tests-check` 只做编译检查，现在使用不带分区对象的独立模块，不再等待 LLVM 分区编译。
- 自托管后端生成的帧没有 unwind 信息，报错堆栈在这些帧之后可能不完整。

验证：29 个运行时用例的输出与日志，和 cli 单编译单元 zxc 一致；`packages/cli` 以 64 分区运行 `test-runtime`，30/30 通过。

### 当前测量（改 1 个 ZX 后重建）

| 阶段                                       | 耗时                 |
| ------------------------------------------ | -------------------- |
| zig build 启动与配置                       | 约 0.5 秒            |
| 生成器（infer 0.57、emit 1.25、写出 0.15） | 约 2.0 秒            |
| 被改分区（自托管）                         | 0.45 秒              |
| Apple ld 链接                              | 0.28 秒              |
| 合计                                       | 3.8 秒（原 12.5 秒） |

### infer 与唯一性分析的再拆解

- **infer 0.57 秒：**
    - 可达性与解析 70 毫秒，签名 68 毫秒，逐模块 mixed 编译 406 毫秒。
    - mixed 编译中，ZX 模块分析 249 毫秒、链接进共享表 70 毫秒、RX 模块 53 毫秒。
    - 模块分析里有正比于整张共享表的工作，总量为“模块数 × 类型数”：
        - `nominal_origins.seed` 每个模块都重新校验整张 nominal 表，再深拷贝其中的字符串。可信的共享表现在改为借用，模块分析降到 187 毫秒，infer 降到 0.5 秒，生成结果逐字节不变。
        - `shared_seed.resolve` 的合并预检约 40 毫秒，由 ZX 实现的预检逻辑生成，暂未改动。
- **唯一性分析：** 一次构建共做 6,276 万次 level 计算，分布在 24,268 次函数体分析中，平均每次约 2,600 次，几乎覆盖整个函数体的全部槽位，合计约 0.75 秒。每次重新分析都从头计算整个函数体，而触发重新分析的只是某个 callee output 或自身 input 的变化。要再大幅下降，需要按依赖精确失效：只重算读到已变 summary 的槽位。前提是保持与 FIFO 求值完全相同的结果。

### 唯一性分析的持久化 memo

单次函数体分析只取决于以下状态，是一个纯函数：

- 函数体内容；
- 全程序形状：类型表，各函数的 I/O 类型与 external 标记，以及 basis；
- 自身的 input summary；
- 所调用函数的 output summary；
- 自身的 normalized/renewed 集合。

`uniqueness/memo.zig` 以这些内容的 Blake3 摘要为键，记录三类结果：

- settle 阶段：每次调用按槽位传给被调函数的 level 和 output；
- demand 阶段：需求标记，以及最终的 normalized/renewed 集合与 `grew`；
- final 阶段：flags 与 renewals。

命中时按原顺序回放：对当前状态重做 meet/join，所以 FIFO 工作队列的顺序和最终结果都与重新分析完全相同。单次运行内，第 2、3 轮约 40% 与 99% 的分析可以回放。

- **持久化：** 记录存进生成缓存 storage 的一条固定记录。header 中的生成器摘要保证生成器一变记录即作废；每次只保存本次用到的条目，内容没有变化时不重写。
- **体积：** 记录约 6 MB。最初按 (callee, slot, level) 逐项存储，有 25 MB；同一次调用的槽位总是连续的，所以改为每次调用存一串 level。
- **一致性验证：** 用上次的 memo 增量运行，再对同一份改动后的源码做完全干净的构建，比较两份输出：
    - 只改循环步长（`contains.zx`）：0 处差异；
    - 给 push 之前的列表加别名、破坏线性使用（`finish.zx`，有 2 个文件重新生成）：0 处差异。
- **收益：** 缓存命中时 emit 从 1.1 秒降到 0.55–0.6 秒，改 1 个 ZX 后的重建从 3.8 秒降到 3.0 秒。
- **局限：** 函数编号是键的一部分，增删函数会让其后的函数全部失效；类型表或 basis 一变，所有记录都会失效。

### 达到毫秒级还缺什么

剩余开销都来自“每次全程序重做”和“每次新起进程”，局部优化已经接近上限。还需要完成：

1. **常驻进程。** 生成器以 watch 模式常驻，把解析结果、infer 结果和 genz 分析状态留在内存中，省掉启动和全量重载；Zig 侧用 `zig build --watch -fincremental`。
2. **infer 按模块增量。** 以模块签名为防火墙：改函数体但签名不变时，只重新分析该模块，再增量链接进共享表。
3. **唯一性分析增量。** 先消除顺序依赖，再以函数 summary 为边界：只有被改函数的 input/output summary 变化时，才向调用方或被调方传播。
4. **Zig 侧增量。** 自托管后端加 `-fincremental` 可以做到函数级的原地补丁，配合常驻进程，避免每次重编整个分区并重新链接。

### infer 的剩余结构性开销

计数插桩（一次构建）：

- 共享类型表约 2,200 个类型，`appendFrom` 被调用约 4,000 次。每次都把前缀（累计 560 万行）逐行和目标表比较，并初始化等长的映射，而真正新增的类型累计只有 2,642 个。

- 给类型表加哈希索引，由 ZX 的 find 消费；
- 可信前缀跳过逐行校验。

这涉及 ZX 合并逻辑与宿主存储之间的契约，尚未实施。另有解析约 30 ms、按路径线性查模块约 15 ms。

### Zig 侧实测上限

- **`zig build --watch`：** 改 1 个文件到二进制更新为 2.56 秒，一次性构建为 2.55–3.07 秒，只省掉启动开销。

- **`-fincremental`：** Zig 0.17 在 macOS 上不可用，Mach-O 链接器在加载目标文件或归档时直接 panic（`TODO(MachO2): load object/archive`）。函数级原地补丁目前在本平台不可行。

结论：用 zig build 驱动时，改 1 个 ZX 后的下限约为 no-op 0.67 秒 + 被改分区 0.45 秒 + 链接 0.3 秒 ≈ 1.4 秒，与生成器无关。要进入毫秒级，必须绕开 zig build 的逐步骤进程模型，并等待 Zig 的 Mach-O 增量链接；或者把编辑循环放进常驻进程，只重编、重链被改的部分。

Zig 默认的 panic 处理器会把整套栈回溯支持编进每个分区，包括 DWARF、Mach-O 符号加载、线程化 I/O 和信号栈。Debug 版 zxc 的 174 MB 代码里，约 125 MB 是这 66 份重复。改为转发后：

- 单个分区编译：0.3 → 0.1 秒；

- 分区改用 ReleaseFast/Small：0.29–0.32 秒，差别可忽略。
- ld 的 `-no_deduplicate`、`-dead_strip`：无改善。
- `zig build --watch`：同样约 1.45 秒（当时），不省时间。

### 实测：按依赖层提前分析不划算

做过一版完整实现（未提交）：

- 链接仍严格按原依赖序进行，保证函数号与类型号不变；
- 依赖已链接的模块按轮次在多核上提前分析；
- 每轮持有一份共享表副本，因为链接会扩容并释放旧缓冲；
- 链接时，新函数排到当前表尾，类型从快照的计数起按结构去重合并；
- preflight 的界限放宽为 `first ≤ 目标表长度`。

结果：生成内容与顺序版逐字节一致，但 infer 从 260 ms 变为 420 ms。原因有两个：

- 依赖图近似一条链：1416 个模块需要 560 轮，344 轮只有 1 个模块；只有第一轮有 152 个可并行。
- 即使是第一轮，32 线程也只有 1.2 倍加速（14 ms 对 16.8 ms），分配与缺页争用抵消了并行。

结论：在这张依赖图上，并行化 infer 没有空间。要继续缩短 infer，只能跳过未变模块的重新分析，也就是常驻进程或持久化按模块的分析结果，使一次编辑只重新分析被改模块及受影响的下游。

## 实施记录：常驻生成器与跨请求模块复用

改 1 个 ZX 后的端到端重建从约 1.09 秒降到约 0.85 秒，生成器在 0.47 秒时完成。生成器内部 infer 从约 260 ms 降到约 100 ms。

### 常驻生成器

- 首次构建照常冷生成，结束后在缓存目录的 `generator.sock` 上启动一个常驻副本（`build/resident/service.zig`）。之后的构建把请求转给它，它在内存里保留解析结果、生成缓存和上一次分析。
- 副本与可执行文件的路径、大小、修改时间绑定。生成器重新编译后，旧副本收到请求会回复 stale 并退出，客户端冷跑一次再启动新副本。工作目录不同则拒绝。副本空闲 15 分钟后退出。
- 副本处理失败时，客户端在本进程重跑，诊断照常输出到构建。设 `ZXC_RESIDENT_GENERATOR=0` 可关闭。
- 启动副本时会把构建器进度管道的描述符设为 CLOEXEC，并从环境里去掉 `ZIG_PROGRESS`。否则构建器会一直等这个管道关闭。

只常驻、不复用分析结果时，收益很小：parse 全部命中缓存后，infer 仍有约 230 ms，耗时几乎都在按依赖序逐模块做语义分析。

### 跨请求模块复用（`rx/analysis/project/history.zig`、`mixed/reuse.zig`）

- 混合分析按依赖序把各模块链接进只追加的共享表。每个模块开始和结束时，记录各表每一列的长度作为检查点。
- 下一次分析从相同的初始表出发。判定条件：
    - 帧摘要相同。帧摘要覆盖 RX 源、清单和接口；任一 RX 源改动都会让分析全量重跑。
    - 初始各列长度相同。
    - 类型、名义来源和签名函数行逐项相等。
- 满足条件时逐模块推进。如果某个 ZX 模块源码摘要不变，且它的依赖都没有被重新分析，就把上次该模块追加的行原样拷入新表，不再分析。
- 分析会读取被调函数的函数体（错误效应、任务安全性），而不只是签名。所以依赖了重新分析过的模块的模块，也必须重新分析。RX 模块总是重新分析。
- 重新分析的模块如果追加了不同的类型或不同数量的行，表就不再对齐，此后的模块全部重新分析，退化为从该点回滚重放。
- 被拷入的行仍指向上一次分析的内存、请求输入和解析结果。因此常驻副本按 epoch 保留这些 arena，解析缓存也暂留被替换的解析结果：
    - 一次完全未复用的分析之后，释放所有更早的 epoch；
    - 保留量超过 1.5 GB 时，下一次强制全量分析。每次增量请求约保留 55 MB。

### 后续：只改函数体时复用前置推导，以及生成器常数项

| Apple ld 链接 | 约 210 ms | 约 115 ms | 开发构建不再嵌入 59 MB 官方 Zig 归档：zxc 二进制从 134 MB 降到 55 MB。见下文                                                                                                                                                                                                       |

端到端约 0.56 秒：

| 环节           | 耗时      |
| -------------- | --------- |
| 生成器步骤     | 约 100 ms |
| 被改分区       | 约 120 ms |
| 链接           | 约 115 ms |
| zig build 自身 | 约 230 ms |

所有改动均与同输入冷生成逐字节一致。

- **嵌入 Zig 的代价：** 实测一个 79 MB 常量段让 ld 多花约 70 ms。用 `-sectcreate` 或 `-no_uuid` 都省不掉，因为成本在写出本身。
- **开发构建的取舍：** 现在只有发布打包传 `-Dembed-zig=true` 才嵌入。开发构建从本机构建缓存读取同一归档，并核对 SHA256。
- **非嵌入发布包：** 发布时同时产出 `-no-zig` 包，由 `ZXC_ZIG` 指定 Zig。
- **生成器的优化级别：** 调试构建时，生成器根模块用 ReleaseSmall，编译约 23 s，运行期没有向量化。改成 ReleaseSafe 后编译约 49 s，单次增量约省 30 ms（emit 58 ms，fixpoint 17 ms）。生成器只在编译器 Zig 源变化时重编，且每次重编多付约 26 s，所以保留 ReleaseSmall，优化走算法层面。
- **试过但放弃的方案：**
    - 按编码字节缓存 memo 摘要：ReleaseSmall 下 StringHashMap 查找比 Blake3 还慢，fixpoint 从 27 ms 变成 60 ms。
    - 函数源码借用生成缓存、不再复制：同一进程内多个库共用缓存时，后一个库替换同名单元会释放前一个包仍在用的文本。
- **剩余的大项：**
    - 唯一性 fixpoint：3 轮约 2.3 万次 memo 命中，每次约 1 µs，合计约 17–27 ms；
    - inline prepare 约 9 ms，其中 value_call 分析占一半；
    - 函数文件指纹约 10 ms。

    这三项都需要跨请求的提前截止，即确认输入不变时整段跳过。zig build 自身的约 230 ms 来自每个步骤起一个 zig 进程做缓存检查，不在 zxc 编译器内。

### 后续：唯一性分析按轨迹提前截止，以及生成器其余常数项

只改一个函数体后重建：

| 阶段                       | 之前      | 之后     |
| -------------------------- | --------- | -------- |
| emit                       | 约 57 ms  | 约 24 ms |
| write                      | 约 17 ms  | 约 10 ms |
| 生成器步骤（含进程与 IPC） | 约 100 ms | 约 55 ms |

端到端仍约 0.53 秒。剩余开销基本在 Zig 一侧：

| 环节                           | 耗时      | 备注           |
| ------------------------------ | --------- | -------------- |
| 被改分区编译                   | 约 120 ms |                |
| 链接                           | 约 115 ms |                |
| cache-identity                 | 约 60 ms  | 与分区编译并行 |
| zig build 启动与各步骤缓存检查 | 其余部分  |                |

产物均与同输入冷生成逐字节一致，含强制走回退路径时。

1. **唯一性分析的轨迹（`uniqueness/trace.zig`）。**
    - **轨迹内容：** 常驻 memo 额外保存上一次分析的轨迹，按函数体记录每次访问得到的结果，以及该访问 memo 键里的状态字节（不含函数体 identity）。轨迹只在内存中，不落盘。
    - **适用条件：** 程序形状与导出不变，且改动的函数体调用的仍是同一组函数。分析是确定性的，所以只要改动的函数体在每个记录的状态下得到相同结果，其余函数体就会遇到与上次完全相同的状态。
    - **提前截止：** 先把改动的函数体放回记录的每个状态（先查 memo；未命中就把状态字节解码回 summaries 与成长副本，再分析一次），逐一比较 settle 与 demand 的结果。全部一致时跳过整个不动点：其余函数体的计划直接取自轨迹，只有改动的函数体在最终状态下重新计划。
    - **回退：** 有不一致时清掉 summaries 的需求标记和成长副本，改走回放。回放时未改函数体按轨迹取结果，不算 memo 键；改动的函数体照常分析并与记录比较，第一次不同之后全部回到 memo 路径。demand 结果里的成长副本按集合比较，列出顺序不同不算分歧。
    - **效果：** 唯一性分析从约 25 ms 降到约 6 ms，不再是 emit 的关键路径。
2. **memo 键。** 去掉 identity 已覆盖的被调序号，计数改为 4 字节，level 按字一次打包四个。格式升到 v4。
3. **按列读取。** 以下几处原先都解码整行表达式，现在直接读 kind 与 payload 列：
    - basis 收集调用与列表写入；
    - 状态值分析查找相等比较。

    函数输出类型的列表槽按类型只算一次。

4. **inline 计划只算纯度。** 计划只读 `pure`，不再跑完整的 value_call 分析（其中状态值分析占大头），约省 4 ms。
5. **write 阶段。**
    - **输出清单按位置比较：** 前后两次写出的文件顺序相同，只在列表不一致时才建路径表。ReleaseSmall 下每次字符串哈希表操作约 250 ns，原先每个文件 4 次，合计约 5 ms。
    - **签名搜索窗口：** 首个窗口从 4 KiB 缩到 512 B，生成的签名最长约 330 B。
6. **复用的函数源码。** 仍由 bundle 持有：已有测试约定缓存销毁后 bundle 仍有效，所以不借用缓存文本。改为先统计总长、分配一块缓冲，再按搜索取回的文本多核复制。复制在记录缓存之前完成，替换同名单元不会释放待复制的文本。
7. **生成器输入指纹。** 常驻文件缓存同时保存每个文本的 Blake3 摘要，指纹只对改动的文件做全文哈希。生成缓存键的字段先攒进 4 KiB 缓冲再整段做 SHA-256，字节流不变，旧缓存键继续有效。

剩余可做的项：

- **源码目录遍历与逐文件 stat：** 约 5 ms。可以按目录 mtime 缓存列表，或改用文件系统事件。
- **RX 模块解析：** 约 2 ms，可按文本指针复用。
- **分区布局扫描：** 在多核上做字符串表查找，每次约几毫秒。
- **被改分区的 Zig 编译与链接：** 共约 235 ms，最大的一块。属于 Zig 侧，可选方向有：按编辑把热点函数移入单独的小分区，或者等 Zig 的增量链接。

### 后续：生成体积与冷生成

本轮针对冷生成和生成代码体积。冷生成指没有生成缓存时的整轮生成，固定 49 入口自举，ReleaseSmall 生成器：

| 指标                   | 之前        | 之后      |
| ---------------------- | ----------- | --------- |
| 生成的 Zig 总量        | 46.4 MB     | 17.3 MB   |
| emit（冷）             | 约 1,364 ms | 约 930 ms |
| emit（只改一个函数体） | 约 24 ms    | 约 24 ms  |

每一步都与改动前的产物逐字节一致（第一项除外，它本身就是删除死代码），增量产物与同输入冷生成一致。

1. **按需生成指针调用变体。**
    - **问题：** 每个函数文件都生成指针 ABI 的 `call`。但值函数的调用方几乎只走 `callValue`：903 个 `call` 没有任何引用，占 46 MB 中的 27 MB。Zig 不会分析未引用的函数，但 genz 仍要降级和打印它们，Zig 也仍要解析。
    - **做法：** 值函数的文件现在只含 `callValue`。后端扫描入口与函数文件中的 `@import("…")).call(` 引用，把被引用的值函数连同 `call` 一起重新生成，直到闭合；共 34 个。
    - **缓存：** 带 `call` 的版本是独立缓存单元，与只含值变体的版本同时常驻。
    - **共用：** 向量化子串搜索从分区步骤移到后端，两处扫描共用。
2. **类型表达式按需构建。**
    - **问题：** 导入共享类型包的函数文件，原先为程序的全部类型构建类型表达式，并为每个状态值类型做一次 SHA-256 命名，占函数文件生成时间的四分之三。
    - **做法：** ABI 与状态两套表初始为空，Lower 通过访问器在首次使用时构建。自带类型声明的文件仍一次建完。
3. **错误集按程序算一次。**
    - **问题：** 每个函数生成时，都沿可达调用图遍历全部函数体来求签名里的错误集，程序整体呈平方复杂度。
    - **做法：** `error_effects` 先在多核上求每个函数体自身的效应，再按调用图强连通分量自底向上合并（Tarjan）。Lower 只遍历正在降级的函数体，被调函数直接查表。本体表达式用位集记访问，错误名用短列表去重。
    - **修正：** 生成缓存键对每个被调函数也写入它的错误集。调用方签名列出被调方的错误，原先被调方新增错误时调用方会命中旧缓存；现在会重新生成：实测给 `header/fail.zx` 加一次下标访问后，它和 5 个调用方一起重新生成，产物与冷生成一致。

冷生成的剩余构成与发现：

- **唯一性分析：** 约 530 ms，单线程，是冷生成的关键路径。其中 settle 约 390 ms：第一轮约 1,400 个函数体共分析 5,418 次，第二轮再分析 2,721 次。
- **工作表顺序：** 按下标从小到大优先改为 6,070 次，从大到小改为 9,589 次，都比现在的 FIFO 多。
- **顺序会改变结果：** 从大到小时外层只跑两轮，8 个模块的产物不同，说明结果依赖访问顺序，不只是代价不同。所以不能直接改成 Jacobi 式并行轮次：并行前要先弄清哪里依赖顺序（函数体分析中对自身输入的就地 meet、budget、成长副本的累积），并证明并行后结果仍然安全。
- **Zig 侧：** 被改分区的 Zig 编译约 0.10 s，其中空分区的固定启动约 65 ms，生成代码本身约 35 ms。

### 后续：冷生成上多核

本轮继续压缩冷生成，同一固定入口与生成器：

| 指标                   | 之前      | 之后        |
| ---------------------- | --------- | ----------- |
| emit（冷）             | 约 930 ms | 约 470 ms   |
| 唯一性分析（冷）       | 约 620 ms | 约 330 ms   |
| emit（只改一个函数体） | 约 24 ms  | 约 25–35 ms |

除第二项修正了缓存键外，每一步都与改动前的产物逐字节一致；增量产物与同输入冷生成一致；1,374 个语料文件的 zxc 输出与基线二进制一致。

1. **唯一性分析的顺序依赖。**
    - **原因：** 函数体分析的传递函数不单调。例如对未带头部的列表 `push` 会复制出新缓冲，结果为唯一；对带头部但不唯一的列表 `push` 则可能就地追加，结果不唯一。已知事实变弱时，结论反而可能变强。
    - **实验：** 改成 Jacobi 式并行轮次（每轮都读上一轮的摘要）后，结果仍然安全，但不动点更弱。7 个模块丢失了 `zxRetract` 归还前沿，1 个丢失了成长副本。栈式的 push/pop 因此每次都要复制，生成代码可能退化为平方复杂度，所以不采用。
2. **唯一性分析预先在多核上分析。**
    - **做法：** 工作表仍逐个访问函数体。队首之后的一段函数体按当时的摘要并行分析，结果记下取得时的时钟。访问时，若本体输入和各被调函数的输出此后都没有变化，就直接采用；否则在本线程重新分析。因此每个结果和工作表顺序都与逐个访问完全相同。
    - **例外：** 自递归函数体会读到自己访问时的改动，不预先分析。
    - **工作线程：** 只启动一次，轮次之间睡在 futex 上。每轮都等全部线程结束，所以不会有线程滞后到下一轮。
    - **数据：** 冷生成约 180 轮，预先分析约 13,500 次，命中 10,265 次，2,670 次因依赖链失效后在本线程重做。
    - **未采用：** 每当队首失效就重新开一轮的策略更差，共开了 2,069 轮，预先分析 19,509 次：失效沿依赖链连锁，每轮都受最慢的函数体拖累。
3. **无身份比较函数集按程序求一次。**
    - **问题：** 每降级一个循环，都遍历全程序的函数体。
    - **做法：** 改为函数事实，在唯一性分析旁边求一次，交给 Lower。
    - **修正：** 函数文件的缓存键对每个被调函数写入这项事实。被调函数开始比较聚合值时，调用方会重新生成，不再命中旧缓存。
4. **生成缓存后台写盘。**
    - **问题：** 1,278 个函数源码逐个原子写入缓存目录，约 166 ms，比并行生成本身（约 70 ms）还长。
    - **做法：** `put` 只收集源码。自举在 emit 结束后另起线程写盘，与写输出和 Zig 编译重叠。缓存之后的任何修改、统计、持久化和 `deinit` 都先等写盘线程结束；期间被替换的源码在写完后才释放。

剩余构成：

- **唯一性分析：** 约 330 ms，仍是 emit 的关键路径；同时运行的其他函数事实只需约 6 ms。冷生成共分析约 16,400 次。几个大函数体（460–1,228 个表达式）因被调函数摘要逐步变弱，被重新分析 25–65 次。要进一步下降，需要按被改变的调用点增量地重算函数体，或使传递函数单调，从而可以按强连通分量自底向上调度。
- **infer：** 约 240 ms，分散在 seed 分析器的各阶段，没有超过 15% 的单点。
- **函数文件生成：** 并行部分约 70 ms，32 线程利用充分。

### 后续：异步预分析、共享线程与常驻预热

| 指标                                   | 之前        | 之后          |
| -------------------------------------- | ----------- | ------------- |
| emit（冷）                             | 约 470 ms   | 约 293 ms     |
| 唯一性分析不动点（冷）                 | 约 250 ms   | 约 160–175 ms |
| 生成器重建后第一次编辑                 | 约 420 ms   | 约 35 ms      |
| 一次增量生成（客户端观测，含收集源码） | 约 45–50 ms | 约 45–50 ms   |

每一步都与改动前的产物逐字节一致（冷生成多次重复对照、增量与同输入冷生成对照）。

1. **按读取值判定预分析结果。** 每次函数体分析记下它读到的每个摘要槽位及其值。只要这些值仍然成立，重新分析会读到同样的值、走同样的路径，结论必然相同；因此用读取集合代替“本体或任一被调函数的摘要变过”的时钟，判定是精确的。
2. **异步预分析。** 工作表不再等一整轮预分析结束。后台线程从有界环形队列取队首之后的函数体，按当时的摘要分析；摘要用原子字节读写，读取集合保证并发读到的混合状态也只会被精确地判为失效。某个摘要变化时，读它的函数体（即因此重新入队的那些）被标记为过期，在访问前重新排队分析。访问时若结果仍在分析中就等待它，否则取用或在本线程重做。
    - **线程数：** 上限 8（含工作表线程）。32 逻辑核的机器上，线程越多，窗口越大，预分析越容易过期，而且争用拖慢工作表线程本身：31 个后台线程时不动点约 248 ms，8 个约 175 ms。窗口为每线程 16 个函数体。
    - **剩余：** 工作表线程主要在等待“刚改动的摘要所触发的那次分析”，这是 FIFO 工作表固有的依赖链，预分析无法缩短。
3. **共享工作线程。** 各并行循环（错误集、唯一性身份、解析预取、函数源码搜索/复制/生成、普通调用扫描）原来每次都按核数新建并 join 线程，一次构建要创建上百个线程。现在共用一组首次使用时启动、循环之间睡在 futex 上的线程，多个循环可同时使用；常驻生成器只启动一次。
4. **常驻生成器预热。** 第一次构建在本进程完成后才启动常驻副本，副本状态为空，于是生成器重建后的第一次编辑又要全量分析（infer 约 240 ms、emit 约 175 ms）。现在副本启动时先把那次请求再分析一遍但不写输出，期间到达的请求在套接字上排队。

剩余候选（均为较大改动）：

- **infer 并行：** seed 分析器中模块正文分析约占 infer 的 42%（约 85 ms）。模块依赖图共 26 层，前 12 层每层 70–144 个模块，并行度充足；但链接顺序必须保持依赖序才能逐字节一致，按依赖序切出的可并行块平均只有 2.2 个模块。可行做法是“依赖都已链接即在快照上分析、仍按依赖序逐个链接”：链接时结构类型按表中首个匹配去重、名义类型按来源去重，因此结果与顺序分析一致；但需要函数编号的重映射、合并边界检查（seed 与 RX 两套）放宽到快照长度，以及共享表扩容时暂停读取者。冷 infer 预计可降约 70 ms。
- **增量 emit：** 约 27 ms，由每次重跑的整程序分析构成：内联准备约 4.5 ms、函数事实约 10 ms（错误集、无身份比较、RX/ZX 能力分析、唯一性基础）、函数文件约 6.7 ms（全部函数的缓存键与源码复制）。降到个位数需要让这些分析按函数跨构建增量：沿用上一次的函数事实，只重算改动函数并沿调用者传播。
- **写出：** 只在输出目录为空时明显（约 180 ms），瓶颈是文件系统创建文件；并行写入在内核锁上争用，墙钟不降。

### 后续：体积优化下的标准库热点、目录批量读取与整程序并行

| 指标                               | 之前      | 之后        |
| ---------------------------------- | --------- | ----------- |
| 一次增量的 emit                    | 约 26 ms  | 约 14–15 ms |
| 一次增量的 write                   | 约 7 ms   | 约 4 ms     |
| 收集源码与解析 RX（每次请求）      | 约 8.6 ms | 约 1.6 ms   |
| 常驻进程主线程每次增量耗时（剖析） | 约 40 ms  | 约 26 ms    |
| 冷生成尾部写缓存记录（一次性进程） | 约 120 ms | 约 65 ms    |

同样逐次对照：冷生成与构建产物逐字节一致，增量（含原地改写同一 inode、修改 RX）与同输入冷生成逐字节一致。

1. **体积优化构建下的标准库。** 生成器根模块按 ReleaseSmall 编译以缩短重建时间，标准库随根模块同为体积优化，而各依赖模块是 ReleaseFast。LLVM 在体积优化下把数组到整数的位转换回卷成逐字节循环：`std.mem.eql` 超过 32 字节、`std.mem.readInt` 每个字都如此，后者波及 Wyhash（所有字符串哈希表）、SHA-256 与 Blake3。core 新增：
    - `bytes.equal`、`bytes.hash`（与 `std.hash.Wyhash.hash` 结果相同、按字直接加载）和 `bytes.Map`，用于路径、源码与输出的比较、哈希与字符串键表；
    - `Sha256`：x86 有 SHA 扩展时按向量载入块、翻转字节后用与标准库相同的指令轮，摘要相同；其他平台与编译期回落到标准库。生成键、命名、缓存与唯一性身份都改用它，唯一性身份由逐字段小块更新的 Blake3 换成它。
2. **目录批量读取。** 常驻生成器每次对每个源码 `stat` 判断缓存文本是否仍有效。macOS 上改用 `getattrlistbulk`，一次调用取回整个目录各项的 inode、大小与时间；按目录层次在共享线程上并行列举，限 8 个线程（更多只在文件系统锁上等待；并行 `stat` 也同样被内核锁串行化）。
3. **RX 模块解析常驻。** 每次请求都重新解析并校验全部 RX 模块。现在常驻状态保存上一次的解析结果与其文本副本，路径与文本全部一致即复用；替换下来的结果留到下一次 release。
4. **整程序分析并行与去重。**
    - 内联选择逐函数独立，在共享线程上并行；无身份比较先并行检查各函数体并记下被调函数，再按序合并；
    - 状态值的重复检测按输出编号轮次标记，不再每个函数清空整张表，且跳过此前轮次已到达的输出；
    - “输出不含输入”原来在每个调用处沿类型树的每条路径递归，共享字段类型被反复展开；改为每个函数按轮次标记各走一次，并作为函数事实只算一次。
5. **其他。** 解析缓存比较已持有的文本副本而不是每次两遍 SHA-256；生成产物在回复之后释放；缓存记录在 8 个共享线程上写出。

剩余候选：

- **infer 并行与唯一性不动点：** 冷生成约 0.6 s 中，infer 主线程串行约 175 ms，唯一性不动点约 180 ms（8 线程预分析），二者仍是冷路径的主要部分，做法见上一节。
- **按函数增量的事实与生成键：** 增量 emit 剩余约 14 ms，由十余个每次重跑的整程序分析与全部函数的生成键构成。
- **RX 流程每个调用步骤复制共享类型表：** `expression_program.build` 为每个调用步骤复制整张类型表并重建去重表，冷约 36 ms、增量约 1 ms。

### 后续：RX 编辑按模块复用与签名沿用

| 编辑类型（常驻生成器） | 之前                    | 之后                          |
| ---------------------- | ----------------------- | ----------------------------- |
| 改一个 RX 文件         | infer 约 180 ms（全量） | infer 约 23 ms，emit 约 17 ms |
| 改 ZX 函数体之外       | infer 约 36 ms          | 不变                          |
| 全量重分析的间隔       | 约每 12 次函数体外编辑  | 约每 29 次                    |

1. **RX 模块复用。** frame 摘要包含全部 RX 文本，改任一 RX 文件都使全部 1,425 个模块重新分析。现在 History 另带一份不含 RX 文本的 shape 摘要和按路径排列的各 RX 模块摘要。shape 相同、模块集合与依赖序都相同时，RX 模块与 ZX 模块一样：自身文本未变、依赖都被复用即复制上次的行。RX 签名由全部 RX 模块的约束一起解出，所以还要求该模块解出的签名与上次结构相同；共享类型表的初始部分已由对齐检查保证一致，类型编号可直接比较。依赖序必须相同，因为复制的行按绝对位置引用其他模块的函数。
2. **签名沿用。** 每次需要重新推导 frame 时都会重算全部 ZX 签名（约 10 ms）。shape 相同、全部 ZX 源码未变、按相同顺序签名的模块也相同时，上次的签名结果仍然成立，直接沿用；沿用它的分析会让上次分析继续存活。
3. **保留上限。** 复用模块的分析会让之前的分析继续存活，编译器自身每次一百多 MB；上限由 1.5 GB 提到 3 GB，全量重分析的间隔约加倍，进程约 1.4 GB，仍在内存预算之内。

验证：多次语义 RX 修改（改变输出的字面量）、RX 空白修改、ZX 函数体外修改及其组合、恢复，均与同输入冷生成逐字节一致。

剩余：函数体外的 ZX 修改仍要重算签名（约 10 ms）和 frame 中其余推导（RX 准备、约束、类型求解约 15 ms）；签名阶段同样按依赖序追加共享类型表，按模块复用需要与模块复用相同的对齐机制。
