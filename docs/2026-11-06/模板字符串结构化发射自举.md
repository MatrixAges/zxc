# 模板字符串结构化发射自举

## Intent：最终目标

将语言模板字符串的目标 AST 发射完整迁入 RX/ZX，保留字符串、布尔、浮点与整数
的全部行为及原分配策略，继续推进自举而不增加应用运行时层。

## Data：可用证据

起点 9d1c494d，工作区干净。aggregate.sequence 已依次求值并绑定全部插值；随后
templates.zig 才进行格式化。整数通过 32 字节局部数组及 printInt 后 dupe，浮点
使用 allocPrint，最终 mem.concat；该职责不依赖 Lower Map，只更新 serial 与
uses_allocator。Lower.call 还需根据当前 capture 选择 try 或 catch，不能遗漏。

已有 AST header、call、field、block、slice、named、整数文本和 fallible 原语。
补齐通用类型／集合／条件表达式与 variable 语句构造，不增加语言语法或语义桥。

## Edges：边界与限制

- 保持全部插值先求值，再按顺序格式化；格式化的分配失败与 capture 行为不变。
- 每个整数仍先分配 decimal 串号，再分配 digits 串号；保持固定缓冲及标准库调用。
- Source 只生成结构化 AST，文本仅为名称、字面量和应用格式参数。
- 输入列与已有 AST 叶 ID 借用；新增名称及嵌套 AST 数组由目标 AST 拥有。
- 原生算法仅供初始 seed；正式适配器只导入 AST 和发布明确的串号／能力结果。
- 不新增测试，复用现有求值顺序、字符串值、typed capture 与分配失败检查。
- 固定 CPU 约 5.34 秒基线不重置；性能仅测实际受影响路径。

## Answer：交付格式与成功标准

RX 显式连接初始化、逐项格式化和最终拼接，ZX 承担内聚的格式化算法及 AST 构造。
贯通新原语、正式入口、seed 和通用物理导入；核对新旧全部产物、阶段编译、相关
现有检查和累计性能，完成后统一提交推送，确认工作区干净且无未推送提交。

```mermaid
flowchart LR
    A[已求值并绑定的 AST 叶] --> I[RX 初始化]
    I --> F[ZX 按项选择格式化]
    F --> S[字符串 / 布尔 / 浮点 / 整数 AST]
    S --> C[RX 最终 concat]
    C --> N[通用 AST 导入]
    N --> P[统一 printer]
```

```mermaid
flowchart LR
    T[借用类型与表达式列] --> W[Source 临时 AST]
    B[全局 AST 基址与串号] --> W
    W --> O[拥有新增文本的目标 AST]
    W --> R[释放工作区]
    O --> Z[普通 Zig 标准库实现]
```

## 实现与复核

AST 构造收口为通用 ast/context API，Source 模板逻辑只有初始化、逐项类型选择、
boolean/float/decimal 格式化与最终 concat。上下文不持有模板的类型列或业务输入，
可供其他生成职责复用；未将每项 AST 转发包装散放在模板目录。已有通用列构造
继续复用，新表达式 payload 独立组织，避免给全部旧构造器扩大输入列。

把既有 SIMD fallible 原语迁到通用 AST 目录，两个消费方共用 try/catch 构造。
模板的 capture(name/label/failure) 直接借用当前 Lower 数据，所有插值先被绑定，
格式化阶段不重新求值；每项整数仍按 decimal_、digits_ 顺序获取两次串号。

整数代码继续使用 printInt→slice→allocator.dupe，变量为固定 32 字节栈数组；
变量和 break 两条语句按 statement_base+first 形成独立块。最终 concat 始终需要
allocator，由 Source 输出明确的 uses_allocator 和 serial，Native 只发布事实。

表达式与新增 payload、语句与 variable 列分别合并，无重复列。undefined 的无值
payload 用独立计数保持其 tag offset；AST 导入复制文本及嵌套参数数组，未把
Source 临时工作区的指针留给目标 AST。旧模板算法完整保留在初始 seed。

初始引导对导出常量仍只接受闭合标量，因此标准库路径由 const.zx 导出的字段名
在调用点组装，不引入顶层集合常量，也不在调用点重复有语义的裸字符串。

## 验收结果

初始 seed → Source 工具 37/37 构建步骤通过，Source → 下一代 Source 工具
19/19 步骤通过。两代针对当前 145 入口、2289 模块、2040 函数文件生成 4746 个
文件，全部实际产物一致，仅 .zxc-inputs 工具身份不同。35 份相关 RX/ZX 的最终
fmt --check 与 lint 通过，所有新增 ZX 均低于建议 180 行。

- 编译器：21/21 步骤，372/372 现有检查通过。
- CLI：61/61 步骤，34/34 现有检查通过。
- 函数分析专项：48/48 步骤，49/49 现有检查通过。
- 模板求值顺序、typed capture 与 SIMD 联合门禁：46/46 Zig 检查通过；Small 模式
  的 Node SIMD 门禁在 WASM 调试位置断言失败，下述对照保留该失败。
- 模板基础值：39/39 步骤，27/27 现有检查通过，覆盖动态 i64/bool/string。
- 同一 SIMD 驱动在 Safe 模式下通过全部 378 个 Node／WASM 数值案例。

Small SIMD 失败发生于 assembly.ts 的源文件调试位置断言。新工具与此前旧工具
native-default-p2-install/bin/zxc 都在同一断言失败，此前数值运行部分通过。原断言
未修改，未把该项说成 Small 模式通过。使用同一新 CLI 和同一既有驱动，将应用
构建模式改为 Safe 后，f32/f64 的 Node、WASM baseline、simd128 及标量回退全部
通过。该对照排除了本阶段共享 fallible 改动导致的数值回归，不能消除原 Small
调试信息门禁与构建模式不一致的问题。

### 浮点模板的证据边界

未找到现有动态 f32/f64 插值运行夹具，也未按用户约束新增用例。静态逐步复核确认：
使用同一个已绑定的 float ExprId，不增加求值或 f32/f64 转换；同样构造单元素 tuple，
调用 std.fmt.allocPrint(allocator, "{d}", tuple)，并沿用同一 try/capture 及 concat。
统一 AST 导入校验其列类型、长度与表示并拥有嵌套数组，但不检查 ExprId 指向值的
语义类型，后者仍由既有绑定和最终 Zig 类型检查负责。不能报告浮点模板已有专项
运行验证；本阶段对该分支的证据是构造配方与生命周期的静态等价核对。

### 固定输入成本

所有构建结束后，在同冻结 141 入口、2220 模块输入上关闭 resident，每轮空缓存，
新旧工具交替四轮，首轮完整保留，中位取后三轮。全部 2268 文件仅工具身份不同。

| ------------- | ------------ | ------------ | -------- |
| CPU 中位      | 5.29 秒      | 5.31 秒      | +0.02 秒 |
| 墙钟中位      | 1.18 秒      | 1.17 秒      | -0.01 秒 |

## 自我复核与剩余边界

本阶段交付模板发射规则及通用 AST 构造能力，原生适配器只借用输入列、导入拥有
文本的 AST 并发布串号／能力事实。原算法没有因性能差额而撤回，也没有新增动态
运行时或把语句文本拼进生成产物。

基础运行检查通过、浮点分支静态核对及 Small SIMD 共同失败分别记录，不能合并
成“所有模式全部通过”。AST 物理存储、Lower 状态及其他 Native 传递依赖仍未完成
自举；本阶段产物一致不能代替最终的依赖闭包审计和规定的阶段自编译。
