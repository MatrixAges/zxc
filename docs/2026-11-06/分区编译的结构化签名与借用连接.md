# 模块闭包分区与构建峰值优化

## Intent：最终目标

降低Source编译器的后端构建峰值，保持自举、zero runtime、zero-copy及运行性能。
公开模块内部保留普通Zig调用，不把高频原子函数切到不同ABI单元。
完整自举及默认构建接入仍属于持续目标，本阶段不宣称全部完成。

## Data：可用证据

阶段起点为已推送的280ec50e。之前主程序重编单进程峰值仍约3.26GB。
函数名哈希分区会切断热调用链；初次4分区运行CPU达到9.08秒，对照5.36秒。
只内联转发降到7.87秒，导入叶函数降到6.56秒，均不满足原有运行性能标准。
因此改为公开入口完整闭包分区，没有继续扩大任意函数内联阈值。

### 已实现

- `packages/genz/src/analysis/partition/plan.rx`真实编排闭包、排序、容量、初始状态、
  分配；ZX分别实现图遍历、确定性排序、并集成本及分组，文件均低于180行。
- 按闭包大小降序、稳定根索引决胜。分配比较新增源码成本与超出目标容量的成本，
  相同成本优先更小分区；分区内部保留完整依赖闭包。
- Native只扫描现有文件引用、借用/组装索引及大小、调用Source规划并连接平台对象。
  初始seed保留原有哈希布局；正式Source路径使用RX/ZX规划。
- Root、Stub、函数命名空间及顶层聚合全部通过genz AST及统一printer生成。
  删除从Zig文本截取函数prototype的实现，旧seed的必要签名复用实际header构造。
- 参数包仅保存参数只读地址，同步调用结束即失效；转发强制内联。
  原始源码完整树只用于顶层comptime执行，不新增运行库或动态加载。
- 错误码按错误名称稳定排序。原先直接使用反射顺序，真实分配失败检查将
  OutOfMemory误报为Overflow；修正后该路径及整套既有检查通过。
- 生成函数及入口采用一致调试策略。混合调试设置导致Zig本身SIGSEGV，保留了
  日志和macOS报告；完整关闭生成单元调试信息后编译、链接及成品检查通过。
- CLI host等待分区完成，避免多个LLVM上下文与主程序同时达到峰值。
  两种原生后端均复用清单对象缓存；工作任务结束即释放自己的临时arena，
  失败会报告实际退出状态或信号，而非丢失空stderr中的失败原因。

### 正确性与阶段证据

- 新增入口后143入口、2229模块、1990函数文件；原1981函数主体全部逐字节不变。
- 2分区为1023和1127函数文件。独立核对各导出根的递归依赖，均无遗漏、
  无多余函数、无主体变化；分区内部stub数量为0。
- 统一调试设置后compiler 372/372、CLI 34/34既有检查通过，没有新增测试用例。
- 普通Source工具与2分区下一代工具生成4647文件，仅`.zxc-inputs`身份标记不同。
  这证明本阶段生成不动点，不代替完整编译器传递依赖自举审计。
- 克隆真实四组源码，合法修改`maximum_result_fields`从4到3：增量2生成、2170复用，
  与同输入干净生成全部文件一致；恢复后0生成、2172复用，全部文件恢复一致。

### 性能证据与边界

同一冻结141入口/2220模块、resident关闭、交替运行；保留首轮原始样本，取后续
三轮中位数。最终普通与2分区Source工具CPU为5.37→5.30秒，墙钟均1.16秒，
RSS约674→664MB；所有生成文件仅工具身份不同。固定历史同输入CPU约5.34秒，
当前Source运行没有累计退化。

同Native源码、143入口、ReleaseSmall、12核心、正式stage0、保留OS缓存：

| 构建观察              |       普通单元 | 2分区（完整关闭生成调试信息） |
| --------------------- | -------------: | ----------------------------: |
| 该次构建墙钟          |         79.34s |                        62.62s |
| time报告最大单进程RSS | 3,284,992,000B |                2,346,156,032B |
| 构建进程树采样RSS     | 3,300,474,880B |                2,225,045,504B |

树RSS为200ms采样下界，不能视为物理私有内存或绝对瞬时峰值。
两次构建的辅助工具缓存状态不同：普通构建额外编译catalog和bundle工具，分区
额外编译对象缓存工具，因此总CPU 89.91与79.54秒不能直接当公平CPU收益。
后续普通最终主程序单独重编记录为68.07秒墙钟、69.20秒CPU；不混入热构建样本。
以上是依赖缓存保留后的重编，不称为清空所有缓存的完整冷构建。

热构建的未修改后续样本：普通约0.20～0.23秒墙钟/0.76～0.77秒CPU，
分区约0.23秒墙钟/0.94～1.00秒CPU。墙钟在容差内，CPU增量尚未满足相对普通
路径的累计标准；默认分区配置不调整，后续继续处理该开销。

### 热缓存命中的解析前检查

输出指纹原本在模板展开、RX解析之后比较。现在先以排序后的原始ZX、模板路径与
内容摘要，以及原有工具、manifest、RX、原生接口和分区配置生成版本化指纹；
命中后直接返回，未命中才展开模板并解析RX。接口读取失败仍在原有模板、RX诊断
之后报告，且不能命中缓存。没有新增运行库或复制源码正文。

普通旧工具与新工具均使用同一两分区Source实现，关闭resident，交替六轮；每个工具
各有稳定输出目录及缓存。单次生成器命中CPU中位数0.0786→0.0694秒，墙钟
0.0488→0.0402秒。该收益仅属于生成器命中路径，尚未消除整体热构建CPU增量。

新工具自身构建19/19步骤通过。克隆真实143入口源码，分别修改ZX常量、RX返回值、
求解器模板超时和原生接口参数名：四次增量均与对应干净生成的4647文件完全一致，
恢复后全部与原始产物一致；四种依赖都使指纹失效。旧、新工具原始产物仅指纹身份
不同。命中时摘要为空，既有源码生成主体不变；不为本次改动新增测试用例。

原始结果位于`partitions/early-fingerprint-validation/result.json`。

## Edges：边界与限制

- 不以新建专用Zig语义桥代替Source算法；Native扫描、现有header/AST构造、
  seed和平台连接均明确保留为边界，不宣称整个genz或编译器已经完全自举。
- 不更改正常未分区路径的生成主体，不为性能改变错误、求值、所有权或模块契约。
- 不修改安装的Zig工具链，不把构建进程崩溃误报为成品运行崩溃。
- 保留初始失败日志；早期Zig接口适配及脚本空格匹配错误已修正，失败不计性能证据。
- 复用有效证据。一次热构建观测触发真实重编且与其他构建重叠，保留原始结果但
  不将首轮计作热构建性能；后续样本在其他任务结束后取得。

## Answer：交付格式与成功标准

本阶段交付可独立使用的Source闭包分组、结构化连接、稳定错误协议和对象缓存。
使用显式`-Dgenerated-partitions=2`及支持该规划的正式stage0复核；默认配置仍保留。
406项既有检查、阶段产物及合法编辑/恢复证据用于证明上述范围。
默认构建接入、热构建CPU进一步收口、完整冷构建及完整自举依赖审计继续推进。

详细命令、完整日志、性能样本、缓存和闭包核查位于忽略目录
`.zig-cache/cold-build-analysis/partitions/`，不将临时报告提交。
