# 共享名义类型参考

## Intent：最终目标

让多个 ZX 分析入口通过 Context 共享类型表时保留枚举声明身份。同一声明复用 TypeId，不同声明即使名称和成员相同也保持不同。

## Data：可用证据

分析结果提供 `value.ir.types` 和 `nominal_types`。前者存放类型及引用关系，后者记录枚举的 type_id、name、origin。单独传类型表不能恢复枚举来自哪个声明。

调用方式见 [generate.zig](共享名义类型/示例/generate.zig)：把上一结果的类型表和来源表一起传给下一个入口。调用返回后可释放上一结果，新的分析结果拥有独立副本。

```zig
.context = .{
    .types = provider.value.ir.types,
    .nominal_types = provider.nominal_types,
    .contexts = &.{.{ .id = "settings", .type_id = settings_type }},
},
```

同身份的枚举必须有相同成员和顺序。新声明在函数体分析之前完成归并，Context 与入口导入签名因此能直接使用同一枚举 ID。共享类型表的原有 ID 保持不变。

## Edges：边界与限制

- `nominal_types` 可省略；缺失记录的共享枚举保留独立身份，不根据名称或结构推断来源。
- 来源记录的 ID 必须指向枚举，名称必须匹配；重复 ID、重复来源与名称、越界记录均被拒绝。
- 项目分析的 source 是规范模块路径；独立分析使用解析时的 file_name。跨入口须使用同一来源路径，推荐稳定的绝对路径。
- native 身份采用声明组 identity，省略时采用 specifier。legacy externals 仍采用 importer、binding、member，既有四个身份回归失败未在本轮解决。
- Context 只绑定入口；普通导入函数不会自动继承。类型元数据的复制不延长运行时对象的生命周期，宿主仍须保持借用数据有效。
- 本扩展不定义 RX Module 输入输出类型的新语法，也不改变 IR 版本。

## Answer：交付格式与成功标准

示例包含独立的类型提供文件、读取 Context 的入口、生成器及 Zig 宿主。先在 `共享名义类型/示例` 执行 `zig build`，然后执行生成器：

```sh
./zig-out/bin/shared-nominal "$PWD" /tmp/zxc-shared-nominal-output

zig run --dep program --dep zxc_abi -Mroot=host.zig \
  --dep zxc_abi -Mprogram=/tmp/zxc-shared-nominal-output/program.zig \
  -Mzxc_abi=/tmp/zxc-shared-nominal-output/abi.zig
```

本轮输出 `Context output: Second`。结果 JSON 显示 cold/first/warm 名义类型数量均为 1，cold/warm Output ID 均为 11；第二轮复用两个模块。`host.zig` 是针对保存的生成产物编写的示例：改变示例类型定义后，须按新的 ABI 类型更新宿主。
