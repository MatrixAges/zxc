# RX 编码约定

使用 RX 组织应用流程，通过调用 RX 模块和 ZX 函数完成业务需求。先明确每个模块负责什么，再决定如何组合。

## 组织业务文件

按业务用途命名和分组，例如：

```text
checkout.rx
users/
  load.rx
orders/
  create.rx
```

checkout.rx 负责协调结算流程；users/load.rx 负责取得用户信息；orders/create.rx 负责创建订单。

每个普通 RX 文件以 Module 为根。不要给 Module 添加 name，也不要再套一层 Pipeline。模块由完整文件路径区分，因此 users/load.rx 和 orders/load.rx 可以同时存在。

## 声明输入输出

在 Module 内先用 Type 引入类型，再用 Args 声明接口。Type 的 as 必填，from 通常省略 .zx；in/out 使用类型表达式：

```xml
<Module>
    <Type from="./calculate_total" as="Total" />

    <Args in={Total.Input} out={Total.Output} />

    <Call fn="./calculate_total" in={$in} />

    <Return value={$ctx.calculate_total} />
</Module>
```

复杂类型在 ZX 中定义一次，RX 通过别名引用。Type 可以多个，别名不得冲突；Args 置于类型声明之后、编排之前，最多一个。标量可直接写内建类型，没有输入或输出时使用 void。接口约束调用和所有返回路径，保留未使用的声明字段。

只转发完整输入并返回一个 ZX 函数结果时，直接使用：

```xml
<Module fn="./calculate_total" />
```

简写自动继承函数的 Input/Output，不能再添加子标签。需要组装参数、处理结果或增加阶段时使用完整 Module。新编排明确写出 Args，不再使用 Input/Output 标签或 Module.in/out 名称标注。

## 调用其他模块

在 checkout.rx 中组合用户和订单模块：

```xml
<Module>
  <Call module="users/load" in={$in.user_id} />

  <Call
    module="orders/create"
    in={{user:$ctx.load,items:$in.items}}
  />

  <Return value={$ctx.create} />
</Module>
```

module 对本地 RX 按当前文件所在目录填写，通常省略 .rx：

| 当前文件         | module          | 调用的文件    |
| ---------------- | --------------- | ------------- |
| checkout.rx      | `users/load`    | users/load.rx |
| users/profile.rx | `load`          | users/load.rx |
| users/profile.rx | `./load`        | users/load.rx |
| orders/create.rx | `../users/load` | users/load.rx |

引用必须对应实际文件。不要把目录当作模块入口，也不要通过更换路径写法或复制文件来回避循环依赖。

## 调用 ZX 函数

RX 模块中的具体计算使用 Call.fn，例如 users/load.rx：

```xml
<Module fn="load_user" />
```

示例中的业务模块和 load_user 函数需要在应用中提供。Call.fn 和 Call.module 必须二选一，不能同时填写。

### 无返回值的 ZX 函数

ZX 使用 `export type Output = void` 声明无返回值。入口签名仍写 `: Output`，函数体可以执行操作而不返回数据。最小形式为：

```typescript
export type Input = void

export type Output = void

export default function (in: Input): Output {
}
```

Call 不再使用 out；Task.out 可选并表示聚合输出表达式。返回 void 的调用不产生 $ctx 值；fn/module 仍使用 in 传入参数，只有 Input 为 void 的 Call.module 可省略 in。void 表示没有返回值，不是字符串 `"void"`，也不需要返回 `null`。应用的 JSON 输出边界会将 void 输出表示为 `null`。

## 保持排版清晰

RX 与 ZX 默认按 90 列安排内容。长标签按属性换行；长调用、数组和表达式在合法边界换行。字符串、模板和注释原文保留，不为满足列宽切开字面量。文件行数限制是独立的 lint 规则。

非空对象表达式、对象类型以及 RX 属性中的对象始终垂直多行，短对象也遵循同一风格：

```zx
const options = {
    ...defaults,
    enabled: true
}
```

使用项目当前版本的 zxc fmt 格式化，再用 zxc lint 检查；无需为格式化补齐项目依赖或执行应用。

## 复用 ZX 常量

把具有业务含义的裸值集中在对应目录的 const.zx 中，显式声明类型并导出；不限于整数，也包括字符串、浮点值和布尔标记：

```typescript
export const retry_limit: u32 = 3

export const completion_message: string = 'completed'

export const retry_delay_seconds: f64 = 0.5

export const audit_enabled: bool = true
```

消费处直接使用命名导入，不再声明一个同值变量：

```typescript
import { retry_limit, completion_message } from './const'
```

当前支持闭合的标量常量表达式，包括整数、浮点数、字符串、布尔值和枚举值；不执行函数调用、读取 Store 或构造复合对象。常量保留声明类型，跨模块和编译库使用同一导出。需要转换数值类型时显式转换。空集合、循环起点等基础结构值不必机械命名。

## 传递数据

- `$in` 表示当前模块接收的输入。
- `in` 明确传给被调用模块或函数的数据。
- 调用结果通过 `$ctx.<name>` 使用。Call 不接受 name，结果名直接取目标文件名；同一作用域同类结果不得重名，Call 目标名不得为保留名 task。Task 返回值用 `$ctx.task.<name>`，与 Call 名称分开。void 调用仍执行，但不产生结果值。
- `Return` 明确本流程返回的值。

只传递完成当前职责所需的数据。子模块需要调用方已经持有的信息时，把信息放进输入，不要让子模块反向调用上层查询。

不要用全局共享状态代替明确的输入输出。涉及状态修改时，要说明由谁持有状态、如何处理并发，以及失败后业务应处于什么状态。

## 组合与控制流程

| 标签                  | 用途                             |
| --------------------- | -------------------------------- |
| Module                | 一个普通 RX 文件的业务流程       |
| Type                  | 引入带明确命名空间的 ZX 公开类型 |
| Args                  | 声明模块输入输出类型             |
| Call                  | 调用 RX 模块或 ZX 函数           |
| Task                  | 为一组相关步骤命名               |
| Parallel              | 组合可并行的 Task 或 Call        |
| Switch、Case、Default | 按条件选择分支                   |
| Return                | 返回流程结果                     |
| Emit                  | 发出业务事件                     |
| Import                | 声明可选的模块组合依赖           |
| Store 引用            | 声明模块需要使用的 Store 数据    |

直接 Call 不需要重复写 Import。Import 不提供模块别名，也不代表立即执行被引用模块。

Parallel 中的步骤应能够独立处理输入，不能依赖彼此尚未产生的结果。直属 Task 是独立分支，Return 结束该分支，全部分支完成后通过 `$ctx.task.<Task.name>` 公开返回值。顺序 Task 可用 `out={...}` 聚合内部结果，并通过 `$ctx.task.<name>` 公开。未写 out 时仍是局部分组，其 Return 结束所在模块或并行分支。Task.out 与同一任务的 Return 不可同时使用；out 必须用花括号表达式，不能写字符串绑定路径。Task 不能直接嵌套 Task。Case 和 Default 只能放在 Switch 中。

模块不能直接或间接调用自身，这同样适用于条件分支。出现双向协作时，先按[消除循环依赖](消除循环依赖.md)调整结构。

## 对外接口与持续状态

- 对外接口写在 `*.gateway.rx`：Gateway 声明接口配置，Group 组织路径，Route 将入口映射到业务模块。
- 持续状态写在 `*.store.rx`：Store 先声明需要的 Type 来源，再声明 Object，Object 包含 Field。Field.type 使用类型表达式，例如 `type={Model.Settings}`；Type.as 必填且当前 Store 内唯一。

Gateway 和 Store 的 name 表达接口或状态的业务名称，不是普通模块的身份。Store 引用的 as 仅用于 Store 数据命名空间。

具体属性和功能以所用 zxc 版本的公开语言说明为准。不要用接口文件编排普通业务流程，也不要用 Store 代替所有业务输入输出。

## 编写前后检查

- [ ] 每个业务文件都有一句话可以描述的职责。
- [ ] module 指向正确的文件或已声明包模块，fn 对应应用提供的函数。
- [ ] 各调用的输入输出衔接明确。
- [ ] 子模块没有反向调用父模块，模块之间不存在循环。
- [ ] 并行步骤不依赖彼此的执行顺序。
- [ ] 失败处理与最终返回值符合业务要求。

验证业务结果和交付要求见[应用验证与交付](验证与交付.md)。

## 属性字符串与表达式

引号表示字符串，花括号表示 ZX 表达式。写 `in="hello"` 传入字符串，写 `in={$in}` 传入模块输入；`in="$in"` 只会传入字面字符串。对象使用双层花括号，如 `in={{user: $in.user}}`，外层是属性边界，内层是 ZX 对象。

RX 属性值只负责数据引用、组装和简单运算，不执行函数或方法调用，也不定义 lambda 或状态更新块；嵌套对象、模板插值和分支中的调用同样禁止。将 loop、集合处理和其他计算放在 ZX 模块中，用 `<Call fn="calculate" in={$in} />` 编排，再通过 `$ctx.calculate` 连接后续步骤。模块组合使用 Call.module。

表达式内部直接写 `<`、`&&`、模板和注释，不使用 XML 实体转义。字符串中的特殊标签字符仍按 `&amp;`、`&quot;` 等规则转义。调用路径和 Task.name 是静态字符串；`fn="load"`、`module="orders"` 已分别省略 `.zx`、`.rx` 后缀，无需 `.zig`。

Type 来源导出的枚举成员可用于值属性，例如 `Total.Status.Ready`；Store 初值使用当前 Store 声明的别名。不同来源的同名枚举不能互换。

Store setter 使用 `setter={[store.alias.object]}`，版本号及 Gateway 字节上限使用带花括号的静态整数。迁移旧用法时，应区分原先的表达式文本与真正字符串，不能保留旧引号并期望它继续执行代码。

普通 ZX 函数统一声明 `in: Input`，输入不可变，不使用 `owned Input`。列表更新产生新结果，旧值仍可读取或传给其它函数；Task 句柄仍只能等待或取消一次。

默认使用四个空格缩进。单层三元可以保留，多层判断在 ZX 中使用 match；RX 的 value 出现嵌套三元时，使用 Switch 标签组织分支，或把判断移到 ZX 函数，通过 Call.fn 合并后取得判断值。不要把 RX 的修正建议写成内联 match。

ZX 中的 `loop(initial, policy)` 可以直接作为语句执行，不需要为了循环副作用写一个未使用的 `const state =`。需要读取最终状态时再绑定结果。两种写法的条件、状态更新与错误传播规则相同，循环更新块内也可以直接调用 `loop`。
