# 应用验证与交付

交付应用代码前，确认业务行为、文件依赖和失败处理是否符合要求。明确哪些检查实际执行过，不把能够阅读的示例描述成已经可运行的应用。

## 准备验证范围

- 本次修改的 .rx、.zx 文件及其业务职责。
- 所有直接和间接依赖的模块，包括嵌套分支中的调用。
- 输入输出约定、状态所有者以及目标环境支持的能力。
- 预期的正常结果、边界行为、失败处理和一致性要求。

## 检查文件与依赖

1. 从本次业务入口出发，确认每一个 service 都指向预期的实际文件。
2. 继续检查这些文件调用的其他模块，包括条件分支中的调用。
3. 检查应用的其他入口和 Import 声明，避免遗漏未走到的调用关系。
4. 确认没有任何模块沿调用链回到自身；出现环时按[消除循环依赖](消除循环依赖.md)重构。
5. 用应用已有的检查与运行方式验证本次变更，保存实际结果。

不要为了得到成功结果而删掉业务必需的文件或忽略某些分支。一个文件可以正常读取，不代表整个业务流程能够正确完成。

如果当前环境没有可用的检查入口，说明已经完成的人工审查和仍未执行的工具验证。不要编造命令，也不要声称未运行的检查已经通过。

## 检查业务行为

使用应用现有的测试方式，按本次任务需要覆盖：

| 场景       | 需要确认的行为                               |
| ---------- | -------------------------------------------- |
| 正常输入   | 最终输出符合业务要求，模块间传递的数据完整   |
| 边界输入   | 空值、空集合、范围边界等得到明确处理         |
| 子模块失败 | 错误传播和后续步骤符合预期，不假定自动回滚   |
| 状态变化   | 并发版本、重复请求和一致性要求得到处理       |
| 重复调用   | 是否可安全重试，是否会重复产生副作用         |
| 异步流程   | 若目标环境支持，检查幂等、终止条件和重复消息 |

保持测试与业务需求相对应，不根据给定示例硬编码结果。测试文件的位置遵循应用项目约定。

## 说明无环保证的范围

从父模块到子模块检查调用关系，任何一条调用链都不应回到已经经过的模块。父模块先后多次调用同一个子模块是允许的；子模块再调用父模块则形成环。

无环依赖只保证静态模块调用链不会回到自身。它不能单独证明计算函数一定结束、事件不会反复触发，或业务结果必然正确。算法终止、事件收敛和业务不变量需要分别检查。

## 使用目标环境的工具

遵循应用已有的构建、检查、测试和运行文档，确认工具版本及命令含义。区分检查器验证了哪些文件、测试执行了哪些业务场景，以及哪些只是手工审查。

例如修改结算流程，应验证真实的结算入口、订单输入、库存不足时的处理和最终返回值。只展示一段 XML，或直接给出预期结果，都不能说明这条业务流程已经验证。

## 构建函数流程

当前版本支持普通 RX 模块中 Call.fn、Call.service、Return、Task 与 Switch 的应用构建：

```sh
zxc build workflow.rx --out build/workflow

./build/workflow '{"value": 41}'
```

按实际推导出的输入类型提供 JSON；没有输入的模块直接运行可执行文件。需要持续构建时使用 `--watch`，需要指定包配置时使用 `--project pkg.yaml`。类型与所有权错误必须修复后再交付，函数返回的新建集合和借用输入不能混为一谈。

同一个 service 文件在所有调用处共享一套输入输出类型。仅透传输入的子模块可以由调用者确定类型；不相容的调用需要调整业务契约，不能靠调用顺序消除冲突。Import 声明依赖，不表示执行。

普通 Task 是顺序分组，分组和条件分支的结果绑定只在本地作用域可见；Switch 只执行选中分支，Return 结束所在模块或并行 Task 执行边界。非 void 输出必须覆盖全部返回路径。Store 为应用级共享内存状态，不自动保存到磁盘；已提交请求的内存目前保留到应用结束，长期有界回收尚未完成。

Parallel 执行直接、独立的纯计算 Call 或 Task。直属 Task 内顺序执行，Return 返回该分支；通过 ctx.<name> 与直接 Call 的结果一起在汇合后公开。无 Return 的 Task 为 void，不产生结果值；非 void 分支必须覆盖全部返回路径。输入不能依赖兄弟结果，全部分支结束后才公开直接 Call 的命名结果；void 调用仍会执行并传播错误。工作分支不能访问 Store 或原生外部能力，输入中已捕获的 Store 不可变快照可以使用。事件执行仍未接通，证明与 FPGA 已接受独立纯计算 Parallel 的受支持数值类型；全部分支都必须满足契约，void 分支也不能跳过。证明不覆盖操作系统线程资源与调度，FPGA 生成纯函数电路，不保证分支与硬件单元一一对应。`check-rx` 的结构和依赖检查成功不能替代实际构建与运行验证。不要为交付而将未支持的节点悄悄删除。

## 构建 HTTP 接口

```xml
<Gateway name="api" listen="127.0.0.1:8080">
  <Group prefix="/api">
    <Route method="POST" path="/orders" service="orders" />
  </Group>
</Gateway>
```

```sh
zxc build main.gateway.rx --out build/server

./build/server
```

当前版本支持 HTTP Gateway 应用。服务按自己的 Input 类型接收 JSON 正文，Output 转为 JSON 响应；void 输入要求空正文，void 输出为 null。Group.prefix 只影响 URL，service 始终相对 Gateway 文件解析。重复方法与路径在构建时拒绝；省略 method 表示任意方法，GET 不隐含 HEAD。路径必须是完整字面路径，不接受参数和通配符，query 不参与匹配。

默认监听 127.0.0.1:8080，listen 使用数字 IP 与端口；max_header_bytes 默认 8192，max_body_bytes 默认 1048576。路由共享同一应用 Store。当前服务器顺序处理，每连接一次请求，没有超时、TLS 服务端或并发；写请求的长期内存回收尚未完成。其他协议、Gateway 库发布及 `--result discard` 不属于当前接口。交付时应真实请求每类业务输入，并检查错误响应与跨请求共享状态。

## Store 共享状态

Store 用来承担显式全局状态的职责。同一应用实例中的模块和请求共享同一个 Object，启动时初始化一次，应用结束后释放；重启使用初值。单个请求结束不应清空 Store，Module 引用和别名也不创建副本。

通过 Module 声明访问范围，通过 Call 显式传入读取值和写权限。成功的更新发布到共享内存，后续调用读取新值；旧输入和结果在仍被使用时保持有效。一次 Call 最多更新一个 Object，后续失败不回滚此前成功更新。

Store 不自动写文件、恢复快照或要求状态目录。跨重启保存是独立的应用需求，不由 Store 隐式承担。

## 交付说明

简单改动用几句话交代即可；涉及模块重构时，可使用下面的 Markdown 模板：

```markdown
## 变更说明

- 新增或修改的业务文件及其职责。
- 模块如何协作；若修复了环，说明删除了哪条反向依赖。

## 验证结果

- 实际执行的命令与结果。
- 检查覆盖的应用文件和业务场景。
- 未执行的检查及原因。

## 待完成事项

- 尚未完成的业务要求。
- 目标环境缺少的能力或待确认的一致性与失败处理约定。
```

## 交付前检查

- [ ] 所有引用都对应实际业务模块，完整依赖图无环。
- [ ] 没有通过改名、复制模块、回调或事件隐藏反向调用。
- [ ] 输入输出和业务失败路径已有明确约定。
- [ ] 没有把单个样例或工具自身的测试通过，当作整个应用已验证。
- [ ] 未执行的检查、不可运行的方案和未完成需求已如实说明。
