最初の診断を、報告されたソース位置で確認します。最も早い無効な構造を直すと、同じ思い違いから生じた後続のエラーも解消することがあります。

### 診断の形式

```text
path:line:column:code:message
```

コードは失敗の分類を示します。問題を報告する際は、メッセージとソース位置を残してください。分類だけでは通常、情報が不足します。

| コード              | 最初に確認するもの                               |
| ------------------- | ------------------------------------------------ |
| `lexical`、`syntax` | トークン、区切り記号、対応する文法               |
| `unsupported`       | その構文が ZX に存在するか                       |
| `contract`          | ファイルの役割、Input/Output、デフォルト関数の形 |
| `name`、`naming`    | 宣言、スコープ、命名規則                         |
| `type_mismatch`     | スカラーの明示的なビット幅とデータの形           |
| `return_path`       | 必要なすべての経路が値を返すか                   |
| `spacing`           | コンパイラのフォーマッタが期待する空白           |
| `ownership`         | 借用中または消費済みの値                         |
| `module`            | インポートパス、ファイルの役割、循環依存         |
| `capability`        | ホストの登録とアクセス権限                       |

### インポートを解決できない

ファイルが存在すること、`.zx` 拡張子が明示されていること、相対パスがインポート元から始まることを確認します。`@/` の場合はコンパイラプロセスの作業ディレクトリを調べます。型のインポートは型専用ファイルを、関数のインポートは実行可能ファイルを指す必要があります。

### リストを再利用できない

束縛を最初に消費した操作を探します。その操作が返したリストを使い続けるか、独立した二つの所有者が必要になる前にクローンします。消費済みの値を改名しても、所有権は戻りません。

### 整形の検査に失敗する

`zxc fmt file.zx` で整形結果を確認し、置き換える意図がある場合に `--write` を使います。ソースと差があると、`--check` は終了ステータス 1 を返します。このフォーマッタは ZX の空白規則に重点を置いており、汎用 TypeScript フォーマッタではありません。

### XML は検証できてもアプリケーションが動かない

現在の RX パッケージが検証するのは、構築済み AST とモジュールグラフです。XML パーサー、式評価器、スケジューラ、自動的な ZX 結合は含みません。動くサービスとして宣言をデバッグする前に、足りない層を提供するホストを特定してください。

### 再現可能な問題を報告する

ソースのリビジョン、Zig のバージョン、コマンドと作業ディレクトリ、最小限の関連ファイル、完全な診断、期待する動作を含めます。生成 Zig の失敗なら、生成ソースとホスト統合の境界も添えてください。
