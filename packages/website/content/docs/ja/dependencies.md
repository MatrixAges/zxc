### 依存関係を下向きにする

親が子を取りまとめ、子は親を呼び返しません。この規則は直接の呼び出しだけでなく、条件分岐内の呼び出しにも適用されます。

二つのモジュールが互いを必要とする場合は、次を検討します。

1. 共通の計算を第三のモジュールへ移す。
2. 両方を呼ぶ親にオーケストレーションを移す。
3. すでに分かっているデータを明示的な入力で渡す。
4. 一つのモジュールが二つの仕事をしているために循環しているなら、責務を分ける。

同じ子を順番に二度呼ぶことは有効です。呼び出しの連鎖が、その連鎖上にあるモジュールへ戻ると循環になります。

### 循環を隠さない

パスの改名、ファイルの複製、逆向きの呼び出しをイベントの背後へ移すことでは、設計上の依存関係は解消しません。条件分岐と明示的なインポートを含め、到達可能なすべてのモジュールを確認します。

モジュールの依存関係が非循環でも、アルゴリズムの停止、イベントの収束、業務結果の正しさは証明されません。それぞれ別に検証してください。

### 正しい再利用を見分ける

```text
checkout → users/load
checkout → orders/create → users/load
```

このひし形の構造は有効です。二つの経路は同じ依存先に到達しますが、祖先には戻りません。`users/load` を繰り返し呼ぶだけでは循環になりません。

```text
checkout → orders/create → checkout
```

こちらは循環です。共通処理を取り出すか、調整する判断を `checkout` に移します。逆向きの依存関係を改名して隠してはいけません。

### 実行だけでなく宣言を確認する

未使用の ZX インポートや明示的な RX インポートも依存関係になります。グラフは静的な契約なので、条件付き実行を理由に逆向きの辺を許容できません。正規化と解決の規則は[パスとインポート](/docs/module-paths)を参照してください。
