### アプリケーションの境界を検証する

対象アプリケーションで文書化されたビルド、検査、実行コマンドを使います。変更した RX と ZX、その推移的な依存先、実際の業務入口を確認してください。

- すべてのモジュール参照が実在するファイルに解決される。
- 各呼び出し境界で入出力が一致する。
- 依存関係が非循環である。
- 通常時、境界条件、失敗時の振る舞いが業務契約に合う。
- 状態の所有権、並行処理、再試行の振る舞いが明示されている。

### 根拠を正確に報告する

静的解析、コンパイル、ホスト実行、業務上の検証を分けます。コンパイラのビルド成功は、アプリケーションが実行された証拠ではありません。

ランタイムや検査器を利用できない場合は、その制限を明示してください。実行コマンドを作り上げたり、実測の代わりに期待値を示したりしてはいけません。

### 簡潔な報告を引き渡す

変更した動作と各ファイルの責務、実際に実行したコマンドと結果、未解決の要件を記します。失敗を隠さず、成功させるためだけに必要なケースを取り除かないでください。

### 根拠と主張を対応させる

| 検査                  | 裏付けるもの                           | 証明しないもの                               |
| --------------------- | -------------------------------------- | -------------------------------------------- |
| `zxc fmt ... --check` | フォーマッタの出力とソースの一致       | 型安全性や実行                               |
| ZX のコンパイル       | 解析、意味検査、Zig の生成             | ホスト統合や業務上の正しさ                   |
| ホストのビルド        | 生成コードがそのビルドに統合できること | すべての実行経路の正しさ                     |
| ホストでの実行        | 渡した入力で観測した動作               | 実行していない経路の動作                     |
| RX の構造検証         | タグとモジュールグラフの制約           | XML 読み込み、スケジューリング、状態コミット |

### 引き渡しの例

```text
Behavior: <what changed>
Files: <each responsibility>
Toolchain: <revision and Zig version>
Verified: <actual commands and observed results>
Host boundary: <memory, I/O, and state assumptions>
Remaining: <unimplemented or unverified behavior>
```

診断によってコンパイルが止まる場合は[診断への対処](/docs/troubleshooting)、コンパイルできても動かない場合は[ホストとの統合](/docs/host-integration)を確認します。
