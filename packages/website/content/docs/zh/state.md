状态是编译器与宿主之间的显式边界。Store 声明描述数据，实际运行的宿主必须实现如何读取、修改和提交这些数据。

### 区分三层职责

| 层次          | 职责                                     |
| ------------- | ---------------------------------------- |
| RX Store 声明 | 描述对象与字段                           |
| ZX 编译上下文 | 注册句柄与允许的访问方式                 |
| 执行宿主      | 提供值、生命周期、并发、持久化与提交行为 |

当前仓库不会自动把 RX Store 文件链接到 ZX 执行上下文。名称相同，不代表已经形成可用能力。

### 有意识地提供能力

宿主集成通过 `compileWithContext` 或项目编译上下文注册 Store 能力。读写权限彼此独立。生成的有状态入口除 arena 和输入外，还接收宿主上下文。

命令行编译器无法从 Store XML 文件中推断应用专属句柄。编译需要这些句柄时，应使用编译器集成 API。

### 写入状态前，先定义提交语义

对每项操作，明确哪些值属于同一个一致快照、检查哪个版本，以及竞争更新先成功时如何处理。锁、版本、持久化和跨对象原子发布均由宿主负责。

编译器检查不是事务管理器。如果一项操作更新两个对象，而宿主分别写入，仍可能暴露部分更新的状态。

### 将纯计算单独保留

不需要状态的计算，优先使用带类型的输入输出。把所需快照传入纯 ZX 函数，再让宿主按提交策略应用结果。只有确实需要直接访问能力时，才引入 Store 访问。

结构术语见 [Gateway 与 Store 声明](/docs/gateway-and-store)，实现边界见[能力与限制](/docs/capabilities)。
