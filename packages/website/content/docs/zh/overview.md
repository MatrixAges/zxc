zxc 用 **RX 表达业务结构**，用 **ZX 编写原子化逻辑**。它的核心目标是让数据流和数据架构清晰可见，并让业务在不断扩展时仍然可理解、可追溯、可维护。

zxc 把业务结构交给 RX，把原子逻辑交给 ZX。数据从哪里来、经过哪些计算、流向哪里，都通过边界和连接显式表达。编译器检查依赖关系，让结构约束随着业务一起保留下来。

### 分形扩展

一个 ZX 单元负责一项边界明确的计算，RX 将这些单元组合成业务模块。模块再组成更大的业务边界；需要细化时，内部继续拆分。每一层都保持单一职责、显式输入输出和单向依赖，这就是 zxc 的分形组织方式。

这里的“原子”指一项职责与契约明确的逻辑，不是数据库原子事务，也不是越小越好。“分形”指不同层级沿用相同的拆分与组合规则，不是循环依赖或递归调用。显式连接展示数据经过哪些单元，输入输出类型说明边界上的数据形状；无环检查约束依赖方向，但不能单独消除所有业务耦合。

### AI 图谱

编译器内建依赖分析，让文件、调用与类型关系成为可检查的事实。我们希望把这张图谱直接交给 AI：定位相关单元、追踪上下游、判断改动影响，按需获取上下文，让每次修改都有迹可循。

目标是尽可能减少 token 消耗和心智负担，让非 SOTA 模型也能在明确契约与编译器反馈下，写出与 SOTA 模型同等质量标准的代码。

### 原子级优化

边界明确的 ZX 单元可以像计算算子一样被分析和优化。zxc 的静态信息与 Zig 的编译期能力，为内联、特化和消除抽象开销提供路径，让清晰的业务表达与高性能代码朝同一个方向演进。

当前 ZX 编译为 Zig；选用 Zig 的 LLVM 后端时，可继续利用其目标平台优化与机器代码生成能力。零成本抽象是需要用生成代码和性能测量验证的目标，并不意味着每个操作都没有分配或运行时开销。

更长远的方向，是围绕原子单元接入形式化规格与证明、汇编级分析与生成，以及 FPGA 等硬件目标。形式化验证需要专门的证明工具，FPGA 需要综合流程与后端；这些是未来路线，并非 LLVM 自动赋予或当前已交付的能力。

### 能力边界

当前实现与可运行路径见[能力与限制](/docs/capabilities)。不要把设计目标当成已经发布的工具接口或经过测量的性能结果。

### 沿着一条路径，得到可运行的结果

1. 根据计算、组合或宿主能力的需求，[选择集成方式](/docs/choose-integration)。
2. [构建编译器](/docs/getting-started)，执行现有 ZX 示例。
3. 使用明确的输入输出，[编写带类型的逻辑](/docs/write-logic)。
4. 应用需要清晰的工作流边界时，[组合模块](/docs/compose-modules)。
5. 依据实际宿主的能力，[验证交付结果](/docs/validate-and-deliver)。

### 共通概念

| 概念        | 含义                                 |
| ----------- | ------------------------------------ |
| 模块身份    | 规范化后的文件路径，而非任意模块名称 |
| 输入 / 输出 | 跨越计算边界的值                     |
| 依赖        | 导入或服务调用建立的静态关系         |
| 能力        | 宿主显式提供的操作或状态句柄         |
| 所有权      | 哪个绑定可以消耗或保留一个值         |
| 宿主        | 负责执行、内存、I/O 和状态提交的程序 |
