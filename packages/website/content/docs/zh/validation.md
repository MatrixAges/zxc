### 验证应用边界

使用目标应用文档中规定的构建、检查和执行命令。检查所有改动的 RX 与 ZX 文件、它们的传递依赖，以及实际业务入口。

- 每个模块引用都能解析到真实文件。
- 每个调用边界的输入输出一致。
- 依赖保持无环。
- 正常、边界和失败行为符合业务契约。
- 状态所有权、并发与重试行为明确。

### 准确报告证据

区分静态分析、编译、宿主执行与业务验证。编译器构建成功，不代表应用已经运行。

运行时或检查器不可用时，应说明限制。不要编造执行命令，也不要用预期输出替代实际运行结果。

### 提供简短的交付报告

列出行为变化与文件职责、实际运行的命令及其结果，以及未解决的要求。保留失败信息，不要为了通过而删除必要场景。

### 让证据对应结论

| 检查                  | 可以支持                 | 不能证明                 |
| --------------------- | ------------------------ | ------------------------ |
| `zxc fmt ... --check` | 源码符合格式化器输出     | 类型安全或执行行为       |
| ZX 编译               | 解析、语义检查、Zig 生成 | 宿主集成或业务正确性     |
| 宿主构建              | 生成代码能接入该构建     | 所有运行时路径都正确     |
| 宿主执行              | 给定输入下观察到的行为   | 未执行路径的行为         |
| RX 结构校验           | 标签和模块图约束         | XML 加载、调度或状态提交 |

### 建议的交付格式

```text
Behavior: <what changed>
Files: <each responsibility>
Toolchain: <revision and Zig version>
Verified: <actual commands and observed results>
Host boundary: <memory, I/O, and state assumptions>
Remaining: <unimplemented or unverified behavior>
```

诊断信息阻止编译时，参见[处理诊断信息](/docs/troubleshooting)。代码能编译但不能运行时，检查[宿主集成](/docs/host-integration)。
