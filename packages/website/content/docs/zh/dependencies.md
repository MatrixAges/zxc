### 让依赖向下流动

父模块编排子模块，子模块不反向调用父模块。这个规则既适用于直接调用，也适用于条件分支中的调用。

两个模块看似需要互相调用时：

1. 将共享计算提取到第三个模块。
2. 将编排提取到同时调用两者的父模块。
3. 通过显式输入传递已知数据。
4. 如果环来自一个模块承担了两项工作，就拆分职责。

顺序调用同一个子模块两次是合法的。调用链回到链上已有的模块，才构成环。

### 不要隐藏依赖环

重命名路径、复制文件或把反向调用藏在事件后面，都不能消除架构依赖。检查所有可达模块，包括条件分支和显式导入。

模块依赖无环，不代表算法一定终止、事件一定收敛或业务结果一定正确。这些性质需要分别验证。

### 识别合法复用

```text
checkout → users/load
checkout → orders/create → users/load
```

这个菱形结构合法：两条路径到达同一个依赖，但都没有返回祖先模块。重复调用 `users/load` 本身不会形成环。

```text
checkout → orders/create → checkout
```

这就是一个环。应提取共享工作，或将协调决策移入 `checkout`，而不是给反向依赖换个名字。

### 检查声明，不只看执行路径
