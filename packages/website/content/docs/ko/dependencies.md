### 의존성은 아래로 향하게 하기

부모가 자식을 조율합니다. 자식은 부모를 호출하지 않습니다. 이 규칙은 직접 호출뿐 아니라 조건 분기 안의 호출에도 적용됩니다.

두 모듈이 서로를 필요로 한다면:

1. 공통 계산을 세 번째 모듈로 옮깁니다.
2. 두 모듈을 호출하는 부모로 오케스트레이션을 옮깁니다.
3. 이미 알고 있는 데이터는 명시적인 입력으로 전달합니다.
4. 한 모듈이 두 가지 일을 해서 순환처럼 보인다면 책임을 나눕니다.

같은 자식을 순서대로 두 번 호출하는 것은 유효합니다. 호출 체인이 그 체인에 이미 포함된 모듈로 돌아가면 순환입니다.

### 순환을 숨기지 않기

경로 이름을 바꾸거나 파일을 복제하거나 역방향 호출을 이벤트 뒤로 옮겨도 구조적 의존성은 해결되지 않습니다. 조건 분기와 명시적인 가져오기를 포함하여 도달 가능한 모든 모듈을 검증하세요.

모듈 의존성에 순환이 없다고 해서 알고리즘 종료, 이벤트 수렴, 비즈니스 결과의 정확성이 증명되지는 않습니다. 이 속성들은 별도로 검증하세요.

### 유효한 재사용 구별하기

```text
checkout → users/load
checkout → orders/create → users/load
```

이 다이아몬드 구조는 유효합니다. 두 경로가 같은 의존성에 도달하지만 조상으로 돌아가지 않습니다. `users/load`를 반복 호출하는 것만으로 순환이 생기지는 않습니다.

```text
checkout → orders/create → checkout
```

이는 순환입니다. 공통 작업을 추출하거나 조율 결정을 `checkout`으로 옮기세요. 역방향 의존성의 이름만 바꿔 숨기지 마세요.

### 실행뿐 아니라 선언도 검토하기

사용하지 않는 ZX 가져오기와 명시적인 RX 가져오기도 의존성에 포함됩니다. 그래프는 정적 계약이므로 조건부 실행으로 역방향 간선을 정당화할 수 없습니다. 정규화와 해석 규칙은 [경로와 가져오기](/docs/module-paths)를 참고하세요.
