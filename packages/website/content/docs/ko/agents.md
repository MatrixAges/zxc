### 작업 계약

비즈니스 목표, 기존 애플리케이션 파일, 예상 입출력, 실패 시 동작, 설치된 zxc 버전을 제공하세요. 다음 프롬프트로 시작할 수 있습니다.

```text
이 애플리케이션을 zxc로 구현하세요.

목표: <비즈니스 동작>
기존 파일: <애플리케이션 맥락>
입력과 예상 출력: <예시>
실패 시 동작: <요구 사항>
도구 체인과 호스트 런타임: <사용 가능한 기능>

먼저 현재 zxc 문서를 읽으세요.
RX 오케스트레이션과 ZX 비즈니스 로직을 분리하세요.
파일 경로로 모듈을 식별하고 순환 의존성을 방지하세요.
이 환경에서 지원하는 기능만 사용하세요.
변경된 동작, 실제 검증 결과, 남은 문제를 보고하세요.
```

### 전달 계약

애플리케이션 파일, 파일별 책임, 검증 결과, 해결되지 않은 제한을 제공하세요. 읽을 수 있는 XML 예제를 실제 실행된 애플리케이션으로 보고하지 마세요.

### 구조를 따라 문맥 좁히기

관련 RX 비즈니스 모듈을 찾은 뒤 호출과 가져오기를 따라 해당 ZX 단위를 찾으세요. 지역 변경 전에 입출력, 호출자, 상태 권한, 하류 의존성을 확인하세요. 계약이 바뀌면 영향을 받는 사용처도 확인하고, 바뀌지 않아도 새 동작이 사용처의 가정을 충족하는지 검증하세요.

그래프를 AI에 연결하는 목적은 관계를 통해 필요한 문맥을 제공하여 저장소 재독, 토큰 소비, 숨은 추측을 줄이는 것입니다. 현재는 소스와 컴파일러 분석·진단을 사용하며 안정적인 그래프 내보내기 명령이나 완성된 AI 조회 API가 있다고 가정하지 마세요. 비 SOTA와 SOTA 모델에 같은 계약과 인수 기준을 적용하세요. 동등한 품질은 실제 작업으로 평가해야 할 설계 목표입니다.
