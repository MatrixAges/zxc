상태는 컴파일러와 호스트 사이의 명시적인 경계입니다. Store 선언은 데이터를 기술하며, 실행 중인 호스트가 읽기, 변경, 커밋 방식을 구현해야 합니다.

### 세 계층 구분

| 계층           | 책임                                     |
| -------------- | ---------------------------------------- |
| RX Store 선언  | 객체와 필드 기술                         |
| ZX 컴파일 문맥 | 핸들과 허용된 접근 등록                  |
| 실행 호스트    | 값, 수명, 동시성, 영속성, 커밋 동작 제공 |

현재 저장소는 RX Store 파일을 ZX 실행 문맥에 자동으로 연결하지 않습니다. 이름이 같다고 사용 가능한 기능이 생긴다고 가정하지 마세요.

### 기능을 의도적으로 제공하기

호스트 통합은 `compileWithContext` 또는 프로젝트 컴파일 문맥을 통해 Store 기능을 등록합니다. 읽기와 쓰기 권한은 독립적입니다. 생성된 상태 사용 진입점은 아레나와 입력 외에 호스트 문맥도 받습니다.

명령줄 컴파일러는 Store XML 파일에서 애플리케이션별 핸들을 추론할 수 없습니다. 해당 핸들이 필요한 컴파일에는 컴파일러 통합 API를 사용하세요.

### 상태를 쓰기 전에 커밋 의미 정의하기

각 연산에서 어떤 값들이 일관된 스냅샷을 이루는지, 어느 버전을 검사하는지, 경쟁 업데이트가 먼저 성공하면 어떻게 처리하는지 정하세요. 잠금, 버전, 영속성, 객체 간 원자적 반영은 호스트의 책임입니다.

컴파일러 검사는 트랜잭션 관리자가 아닙니다. 연산 하나가 두 객체를 갱신할 때 호스트가 각각 독립적으로 쓰면 부분 상태가 노출될 수 있습니다.

### 순수 계산 분리하기

상태가 필요 없는 계산에는 타입이 있는 입력과 출력을 우선하세요. 필요한 스냅샷을 순수 ZX 함수에 전달한 뒤, 호스트가 커밋 정책에 따라 결과를 적용하게 하세요. 직접 기능 접근이 필요한 곳에만 Store 접근을 도입하세요.

구조 어휘는 [Gateway와 Store 선언](/docs/gateway-and-store), 구현 한계는 [기능](/docs/capabilities)을 읽으세요.
