# 编译器一致性测试

## Intent：最终目标

每个语言特性都从实际 ZX 源码进入编译链，并区分解析、语义、风格、外部 IR 与生成代码运行阶段。采用 [Test262](https://github.com/tc39/test262) 的特性分类、独立断言和阶段明确的负例思想；本项目不宣称 ECMAScript 兼容，也不把 Test262 称为 Node.js 运行时测试全集。

## Data：测试组织

| 目录      | 阶段                | 证据                                            |
| --------- | ------------------- | ----------------------------------------------- |
| frontend  | parse               | 组合子回溯、提交错误、关键字边界、分配失败      |
| language  | parse / analyze     | 类型、表达式、回调作用域、句柄能力、诊断位置    |
| ownership | analyze             | 消费、移动、分支、嵌套别名、clone、冻结         |
| modules   | resolve / analyze   | 类型与函数导入、路径、环、原生注册、依赖诊断    |
| ir        | validate            | 第三方捕获、错误编号/版本、纯类型程序           |
| style     | style / integration | 命名、格式幂等、注释与 Token 保持、编译分配失败 |
| runtime   | runtime             | 从 cases/*.zx 生成 Zig，编译后断言真实值和错误  |

负例要求在指定阶段拒绝，不能以 Zig 编译失败替代应在前端发现的所有权或能力错误。生成测试同时使用输入指针/内容不变、空列表、越界、提交次数和分配预算等独立可观察行为，不能仅比较生成文本。

## Edges：边界

测试全部位于子包 tests，与 src 同级。生成文件由 Zig build 放入缓存，源码中不嵌入 test。测试支持 Debug、ReleaseSafe、ReleaseFast、ReleaseSmall；最终记录说明实际执行过的模式。

Test262 是测试组织参考，不是从上游复制全部 JavaScript 用例。没有把有限测试称为一般正确性证明。宿主 Store 例子验证提交协议，不冒充生产锁或持久化实现。

## Answer：执行

包内执行 `zig build test --summary all`；`test-frontend` 仅执行前端集合。仓库根目录 `zig build test` 已同时连接 RX 和 compiler 测试，不再只覆盖 RX。

增加语法时同时检查正例、对应阶段的负例、作用域/边界，以及至少一个真实生成代码用例；资源相关路径使用 allocator 逐分配失败注入。修改后跑相关检查，最终运行完整构建与约定模式回归。

## 语法覆盖追踪

[33 项语法覆盖表](../../../docs/2026-09-22/语法一致性测试覆盖.md)列出每项语法的正例、负例与运行证据。新增 `negative_parse_test` 和 `negative_semantics_test` 分别验证解析及分析阶段；分析负例必须先解析成功，再匹配具体诊断代码。`runtime/syntax_test.zig` 通过实际生成模块验证运算符、控制流、对象/元组、字符串与集合边界。

[组合与边界扩展](../../../docs/2026-09-22/语法测试组合与边界扩展.md)补充数值类型×操作符、消费方法×所有权状态、多模块错误、真实生成执行及 splice 有界穷举。矩阵的每个静态组合是具名测试，运行参数组合在所属测试内枚举，不冒充独立案例数。
