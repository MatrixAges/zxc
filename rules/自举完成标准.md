# 自举完成标准

## 最终目标

zxc 编译器的自有算法、规则和状态模型必须以 RX/ZX 实现。RX 表达模块编排，ZX 表达逻辑与数据。由编译器生成普通 Zig，并调用 Zig 标准库，不改变源码的实现归属。

静态链接、zero runtime 和零临时分配不能单独证明自举完成。

## 原生依赖边界

- 编译器专用的手写 Zig 实现，无论通过 `zig:`、`std:`、普通模块或宿主直接调用，均属于待迁移内容。
- 待迁移内容包括词法、语法、类型、所有权、模块联结、诊断规则、优化、代码生成，以及 AST、IR、解析栈、类型表和缓存的自有状态模型。
- 专用 Workspace、Writer、Reader、类型转换或命名校验桥可以作为暂时阶段，但必须记明被替代的职责、现有语言能力缺口和移除条件，不能宣称为最终架构。
- 编译器自身需要的通用转换、集合和资源能力，应由普通 ZX 能力或通用标准库契约表达，生成器负责生成相应目标代码。不得将编译器专用语义藏进通用名称下。
- 生成产物使用 Zig 标准库、平台 ABI、链接器和外部后端工具，不等于允许正式编译器回调旧 Zig 的编译器语义。剩余平台边界必须明确列出用途及实现归属。
- 旧 Zig seed 可作为初始引导输入；最终编译器不得依赖它执行编译器语义。

## 迁移原则

以完整职责及其传递依赖为单位验收，不以入口文件后缀或 `zig:` 引用数判断完成率。已有 ZX 算法经 Zig 适配器回调时，算法迁移有效，但适配器及状态桥仍需迁移。

先复用已有普通语言能力。若能力不足，保存可复核的最小表达需求，再完善通用语言能力及代码生成；不得继续用新的同职责专用原生接口作为最终解法。

阶段记录必须区分“逻辑已迁移”“仍有过渡依赖”和“完整职责已自举”。历史阶段成果不因阶段命名自动满足最终要求。

## 最终验收

1. 检查编译器正式入口的传递依赖：自有语义和状态均来自 RX/ZX，手写平台边界逐项说明。
2. 使用 seed 构建 stage 1，再由 stage 1 构建 stage 2、stage 2 构建 stage 3；固定输入、配置及工具链，对约定产物和行为进行核查。
3. 产物一致与依赖闭包检查必须同时成立；共同调用同一手写 Zig 核心的两个产物一致，不算完整自举。
4. 保持 zero runtime 与包职责边界；不得靠解释器、专用运行库或嵌入旧实现替代迁移。
