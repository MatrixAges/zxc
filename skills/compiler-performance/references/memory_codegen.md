# 内存、所有权与生成代码成本

## 先分类复制

遇到 memcpy 热点，沿“采样调用者 → 生成函数/地址 → 原始 RX/ZX → lowering/所有权规则”回溯。优先查以下三类：

- **描述符复制**：Program、ExpressionTable 等大结构按值传递，复制的是列描述符。核对 sizeof、调用次数和反汇编；不能直接称为底层数组深拷贝。若保存字段指针，必须确保指向稳定 owner，不是按值参数的栈上副本。
- **集合复制**：append、更新、快照、持久数组在循环里重新分配并复制旧前缀。长度逐步增长时，总量可能是平方级。
- **慢复制实现**：当前优化级别、标准库或 compiler-rt 生成逐字节循环。先隔离验证配置原因，再决定是否调整数据接口。

`inspect_generated.mjs` 可定位含 `@memcpy`、dupe、renew、reserve、清理出口的文件，但它只做文本统计；不承担所有权证明和 AST 分析。

## allocator 生命周期

画 owner、scratch、缓存及返回值的存活关系。子 arena 挂在长寿命 arena 上时，子 deinit 不保证内存还给真实堆；“调用了 deinit”不足以排除累计驻留。

短寿命草稿用可真正释放的 backing allocator；长期保留结果按需要紧凑发布。同一 owner 内复用工作区并 reset 保留容量，避免频繁映射/归还页面。记录 owner 最终释放点以及并行任务是否已结束。

不能将“换 page allocator 降 RSS”直接当成功：历史实验 RSS 大幅降低但 system 时间和墙钟恶化，复用工作区后才消除代价。生产接口由调用方传 allocator，不硬编码全局分配器。

改复制为借用前，逐字段核对：名称是否借自 parser source，Store/Context 是否比返回值短命，嵌套表是否借自别的 owner，共享列扩容是否让指针失效，调用方是否在缓存销毁后仍使用 bundle。延长一个 arena 无法覆盖多个借用来源；必要的输出所有权复制不能直接删。

## 从保守所有权追到实际复杂度

生成的 printer 曾在重设计后从约 20 秒退化到 95 秒；采样追到 walk 的 append 全部失去增长前沿，导致反复复制。应修复分析或 lowering 的通用规则，不按函数名/案例硬编码放行。

按当前语言语义检查：

- 非就地复制元素的操作，是否被错误判为保留整个源缓冲？元素包含嵌套列表时又是否真实持有？
- 空列表、共享前缀、带 header 的增长缓冲、pop 后 push 的覆盖关系是否被混为一谈？
- 互斥分支的路径信息是否丢失，语句构造期读取与消费顺序是否被倒置？
- 为 shared 列表复制后是否丢失增长元数据，引起后续全链条保守降级？

这些是检查问题，不是通用放宽规则。保留别名可观察性、失效条件和空缓冲边界；先证明唯一性或覆盖安全。静态 renew 数下降后仍需测实际运行时间、缺页和 RSS。

## 去除重复分析与快照

- 可信的增长表：记录已验证前缀，并证明当前前缀仍相同；新增行、根、跨表依赖与外部数据仍校验。共享指针/长度仅在生命周期及不可变性成立时作快速路径。
- 多个逐 origin 查询：语义确为同一个单调最小不动点时，可以批量位集传播、SCC 内迭代；不能把这种证明套到有顺序依赖的所有权分析。
- 稀疏状态快照：未写槽在两个分支均为空且 join 不凭空生成值，才可只记录写过槽位。
- 稠密且稳定的槽位编号可用数组与轮次标记，避免哈希和每轮整表清零；变更布局或重分配后需更新依赖。

## 后端编译成本的放大

源码大小不是唯一解释。LLVM pass 指向指令选择时，看实际 IR 指令和调用数：多个 defer/errdefer 可能在大量 try 出口成倍展开。将同一生命周期的一组缓冲组织成一个清理对象，需保持初始化失败、正常返回和异常返回的清理语义。

按可达需求生成函数变体和类型表达式，跨入口共享真正等价的实现。比较两份生成函数时，归一化入口局部编号和类型序号，保留结构身份，再按 callee 等价关系细化；只去变量名会误合并不同函数，漏类型序号会漏掉重复。文本统计脚本不自动证明等价，不自动删代码。

分区越多不一定越快：每个分区可能重复实例化 panic、栈回溯、标准库泛型和调试信息。检查符号、目标文件和最终二进制组成，避免只调分区数。静态库、源码模块、import 与独立编译单元要分开讨论。
